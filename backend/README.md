# Backend

Go-монолит с ConnectRPC, PostgreSQL, pgx и Squirrel. Реализованы все методы текущих proto:
сессии и вход через Flida, профили, административное создание координатора,
сотрудничество и приглашения, мероприятия и заявки, кошелёк, поощрения и заказы,
чат, геопоиск и загрузка изображений.

Правила предметной области: [domain-design](../docs/domain-design.md).
Состояние реализации и проверки: [backend-implementation](../docs/backend-implementation.md).

Работа с cookie и RPC-ошибками перенесена из Flida в `internal/pkg/cookies` и
`internal/pkg/rpc-error`. Это обычные пакеты основного модуля без зависимостей на
приватные Go-модули Flida и без локальных `replace`.

## Запуск

Из каталога `backend`:

```sh
cp .env.example .env
sh scripts/generate-keys.sh
docker compose up -d postgres
```

Перенесите сгенерированные `SESSION_TOKEN_V4_SYMMETRIC_KEY`, `DATA_ENCRYPTION_KEY`, `ADMIN_API_KEY` в `.env`.
Укажите `FLIDA_ISSUER` и `FLIDA_CLIENT_ID` своего приложения. Flida должна отдавать
OIDC discovery/JWKS и ID token с данными профиля. Если discovery опубликован
по отдельному пути, укажите `FLIDA_DISCOVERY_URL`; issuer остаётся значением `iss`
с `https://`. Для текущей Flida это `https://id.flida.ru` и
`https://id.flida.ru/api/.well-known/openid-configuration` соответственно. Ключи DaData и администратора
остаются только на сервере.

Конфигурация находится в `internal/config`, по подходу Flida: `caarlos0/env`,
разделы с `envPrefix`, `ParseOptions` для типизированных ключей PASETO/AES.
Переменные используют префиксы `POSTGRESQL_`, `HTTP_SERVER_`,
`FLIDA_`, `SESSION_TOKEN_`, `STORAGE_`, `DADATA_`; актуальные имена — в `.env.example`.
Поля Config и вложенных секций публичные, теги `env`/`envPrefix` стоят прямо на них.
Точки входа заполняют Config через `env.ParseWithOptions(&cfg, config.ParseOptions())`,
затем вызывают Validate. Промежуточного environment, геттеров и NewConfig нет.
Сервер ожидает переменные окружения; `.env` сам не читает:

```sh
set -a
. ./.env
set +a
goose -dir migrations postgres "$POSTGRESQL_DSN" up
go run ./cmd
```

Миграции применяются вручную через установленный goose, до запуска сервера:

```sh
goose -dir migrations postgres "$POSTGRESQL_DSN" up
goose -dir migrations postgres "$POSTGRESQL_DSN" status
```

Одна таблица — одна миграция; версии хранит `goose_db_version`.
Сервер не меняет схему автоматически. Рабочие запросы выполняются через pgx/Squirrel.

Единый listener по умолчанию `:8080` обслуживает обычные и административные RPC.
AdminService защищён отдельным `Authorization: Bearer <ADMIN_API_KEY>`;
cookie-сессия волонтёра/координатора административных прав не даёт.
`GET /healthz` возвращает успешный ответ после сборки приложения.
Для браузера нужны HTTPS и `credentials: 'include'`: cookie `__Secure-SID` всегда Secure/HttpOnly.
TLS можно завершать на прокси либо задать `HTTP_SERVER_TLS_CERTIFICATE` и `HTTP_SERVER_TLS_KEY` самому серверу.
`FRONTEND_URL` задаёт адрес фронта для ссылок приглашения.
CORS разрешает любой origin с credentials: сервер отражает origin запроса;
методы и заголовки Connect/gRPC-Web берутся из `connectrpc.com/cors`.
Cookie имеет `SameSite=None; Secure; HttpOnly`, на фронте нужен `credentials: 'include'`.
AdminService подключён к тому же listener и проверяет административный токен до вызова RPC.

Для развёртывания всего проекта используйте [корневой Compose](../docker-compose.yaml)
и [инструкцию запуска](../README.md): frontend, backend и PostgreSQL, постоянные volumes,
ручные миграции Goose и HTTP за вашим Nginx. Образ backend содержит `/app/goose` и миграции;
сервер не применяет их автоматически. Локальный `backend/docker-compose.yml` остаётся
вариантом разработки: PostgreSQL отдельно либо backend с профилем app.

## Первый координатор

Сначала будущий координатор входит через Flida как волонтёр. Вызовите AdminService.FindVolunteers
по ID, телефону или почте и выберите ID будущего координатора. Служебные запросы требуют
`Authorization: Bearer <ADMIN_API_KEY>` на общем listener:

```sh
curl --fail-with-body http://127.0.0.1:8080/admin.v1.AdminService/CreateCoordinator \
  -H "Authorization: Bearer $ADMIN_API_KEY" \
  -H 'Content-Type: application/json' \
  --data '{"volunteer_id":"<ID>","cooperation_request_cooldown_seconds":"60"}'
```

Мероприятия, сотрудничество и поощрения создаются через обычные RPC или интерфейс.
Для защиты подготовьте минимум три мероприятия и три поощрения заранее.
Обычная ручка координатора завершает мероприятие и начисляет коины только после `ends_at`.

## Досрочное завершение для демонстрации

`AdminService.ForceCompleteEvent` завершает опубликованное мероприятие, даже если оно ещё не началось.
Требуется административный Bearer-токен; cookie координатора недостаточно. В `results` передайте
ровно по одному итогу на каждого принятого участника: `confirmed_minutes` либо `absent: true`.
Если принятых участников нет, передайте пустой список. Например, для одного участника:

```sh
curl --fail-with-body "$BACKEND_URL/admin.v1.AdminService/ForceCompleteEvent" \
  -H "Authorization: Bearer $ADMIN_API_KEY" \
  -H 'Content-Type: application/json' \
  --data '{
    "id": "<EVENT_ID>",
    "results": [{"participation_id": "<PARTICIPATION_ID>", "confirmed_minutes": "180"}],
    "request_id": "demo-complete-1"
  }'
```

В одной транзакции фиксируются итоги, часы, коины, операции кошелька и история заявок.
Ожидающие заявки закрываются, чат становится доступен только для чтения, новые заявки запрещены.
Участники и координатор получают realtime-уведомления после успешного сохранения.
Плановые даты сохраняются, время операций соответствует фактическому вызову.
В истории подтверждение записывается от имени владельца мероприятия, как при обычном завершении.
`request_id` общий с обычным завершением: повтор того же запроса не начисляет повторно.
Иные результаты с тем же ключом возвращают `AlreadyExists`; другой ключ для завершённого
или отменённое мероприятие — `FailedPrecondition`. Ошибочные итоги откатывают весь запрос.

## Сборка приложения

`cmd/main.go` — единая точка входа. В `cmd/hahaton` сборка разделена как во Flida:
`init_database_clients`, `init_external_clients`, `init_repositories`, `init_tokens`,
`init_support_services`, `init_services`, `init_rpc_services`, `init_http_handlers`,
`init_http_server`. Сервисы приложения не получают зависимости друг на друга.

## Слои и транзакции

- `api`: фасады сервисов, отдельные RPC, serde и преобразование ошибок.
- `app`: сервисы `ctx, r Request`, проверка запросов и координация агрегатов.
- `domain/aggregate`: состояние, команды, репозиторные контракты и доменные ошибки.
- `domain/model`: отдельная директория на модель, приватные поля, конструктор с Validate.
- `infra`: PostgreSQL-репозитории, Flida/DaData, каталог и локальное хранилище файлов.

Optional-поля app-запросов оформлены по образцу Flida: RPC собирает `RequestOption` через `With…`,
DTO хранит `Optional[T]`, сервис проверяет значение и presence через `Get()`.
Отсутствие поля, пустая строка и явный ноль различаются и при обновлениях, и в фильтрах.

Сервисы не вызывают другие сервисы. Последовательность регистрации и авторизации
собирается в RPC. Репозиторий передаёт callback транзакции; вложенные обращения используют
тот же pgx transaction через context. SQL только читает и сохраняет состояние.
Версий агрегатов, event sourcing, CQRS и специальных механизмов редких гонок нет.

Сессия в context — агрегат Session. Authentication из `internal/pkg/session/authentication/interceptor`
подключён через `authn.NewMiddleware`, как во Flida. ID находится в зашифрованной PASETO-cookie.
Open/Authenticate только устанавливают cookie, Close удаляет текущую сессию из БД.
Volunteer и Coordinator используют общий ID, а наличие координаторского профиля проверяется отдельно.

## Города, изображения и чат

`ListCities`/`GetCity` обращаются к DaData через бэкенд, без чтения и заполнения `cities`.
Ключ `DADATA_API_KEY` хранится только на сервере. `ListCities` ищет населённые пункты
по введённому названию и возвращает до 20 подсказок в порядке релевантности; пустой запрос
возвращает пустой список. `offset` должен быть 0; `total_count` — число возвращённых подсказок.
`catalog_version=dadata` обозначает источник, а не версию полного справочника.
`GetCity` получает населённый пункт по ФИАС-коду. Полная выгрузка городов не поддерживается.
Старые записи таблицы `cities` сохраняются, но больше не используются приложением.

Адресные подсказки также запрашиваются через DaData. Выбранный центр и радиус не передаются
в запрос подсказок и не ограничивают поиск адреса; они применяются только к выборке мероприятий.
DaData не предоставляет проверенные полигоны населённых пунктов: `has_boundary=false`.
Поиск мероприятий по `city_id` возвращает FailedPrecondition; клиент явно выбирает радиус.
Недоступность DaData и исчерпание квоты возвращаются как Unavailable и ResourceExhausted.

UploadImage принимает JPEG/PNG до 5 МиБ и 4096 пикселей на сторону. Ответ содержит
`image_path` для сохранения в карточке и `image_url` для показа. Файлы размещаются в
`storage/{user_id}/{image_id}.jpg|png`, читаются публично через `/storage/`.
Профиль, мероприятие и поощрение проверяют владельца и наличие файла.
Пустой optional-путь очищает картинку, отсутствие поля сохраняет прежнюю.
Helper фронта: `frontend/utils/helpers/image.helper.ts`; привязка полей выбора к формам остаётся задачей UI.

Сообщения чата и секреты приглашений шифруются AES-GCM ключом `DATA_ENCRYPTION_KEY`. Храните ключ между перезапусками:
его замена без переноса данных сделает старую переписку и приглашения нечитаемыми.
Стрим проверяет новые сообщения и право доступа каждые 500 мс. После закрытия/истечения
сессии или отмены участия доступ отзывается; после завершения события остаётся чтение.
При первом и повторном вступлении видны только новые сообщения.

## Проверки и ограничения демо

Интеграционные тесты репозиториев устроены по образцу Flida: testify/suite и require,
`tests/integration/repository/<агрегат>/postgresql`, контейнерный helper в
`pkg/testcontainers/postgresql`. Нужен запущенный Docker; отдельный PostgreSQL/DSN не требуется.
Каждый из 12 suites поднимает PostgreSQL 17, применяет Goose и очищает свои таблицы перед тестом.
Контейнер удаляется автоматически. Рабочая БД не используется.

```sh
go test -tags=integration -count=1 -p 2 ./tests/integration/repository/...
go test -tags=integration -count=1 -p 2 \
  -coverpkg=./internal/infra/repository/... -coverprofile=repository.cover \
  ./tests/integration/repository/...
go tool cover -func=repository.cover
```


E2E-тесты находятся в `tests/e2e/rpc`: сгенерированные Connect-клиенты и testify,
как во Flida. Вместо общего dev-окружения suite поднимает изолированный PostgreSQL 17
через Testcontainers, применяет Goose и запускает `hahaton.Run` в отдельном процессе
тестового бинарника. Используется настоящий общий HTTPS listener для пользовательского и административного API.
Flida OIDC/JWKS и DaData заменены локальным TLS-сервером; подпись ID token и проверка TLS
остаются включены. Реальные учётные записи, ключи провайдеров и рабочая БД не нужны.

```sh
go test -tags=e2e -count=1 -v ./tests/e2e/rpc
go test -race -tags=e2e -count=1 ./tests/e2e/rpc
# Отдельный сценарий без проверки полного покрытия всех ручек:
go test -tags=e2e -run 'TestRPC/TestConcurrentLastEventPlace$' ./tests/e2e/rpc
```

Проверяется успешный вызов каждой из 58 RPC; контроль сверяется с protobuf descriptors.
Дополнительно проверяются права, четыре варианта неавторизованного доступа ко всем 50
защищённым RPC, валидация, optional-поля, повторы, возвраты и живые стримы.
Десять групп параллельных сценариев проверяют места, остатки, баланс, повторные команды,
прекращение сотрудничества, завершение/отмену мероприятия, одобрение/отмену участия и выдачу/возврат.
Отдельно проверяются одновременные начисления общим волонтёрам от двух координаторов.
Данные готовятся через RPC; только часы тестовых мероприятий переносятся в прошлое SQL-фикстурой,
чтобы не ждать реального окончания. Все результаты и бизнес-инварианты проверяются через RPC.
Контейнер, процесс и временные файлы удаляются автоматически; нужен запущенный Docker.


```sh
go build ./...
golangci-lint fmt
golangci-lint run ./...
```

Линтер перенесён из Flida, длина строк — 120. Unit-тесты по договорённости не добавлены.
Для воспроизводимой проверки всех 58 RPC через HTTP с PostgreSQL:

```sh
INTEGRATION_POSTGRESQL_DSN="$POSTGRESQL_DSN" go test -count=1 -tags=integration ./integration
```

Проверки создают отдельную временную схему и удаляют её после завершения;
к рабочим таблицам не обращаются. OIDC/JWKS и DaData подменяются учебными серверами/ответами.
Без `INTEGRATION_POSTGRESQL_DSN` сценарии пропускаются. Это интеграционные проверки;
unit-тесты не добавлены.

На отдельной PostgreSQL 17 проверены goose Up/Down/повторный Up, полный сценарий MVP,
повторы начислений и покупок, нехватка баланса, возвраты, история выданного,
каскады прекращения сотрудничества, доступ к чату, шифрование и cookie-аутентификация Connect JSON.
Отдельно проверены OIDC discovery/JWKS с подписанным учебным токеном, загрузка и привязка
изображения, защита admin API отдельным токеном, полный импорт 1103 записей CSV и чтение без исходного файла,
Connect-стрим с историей, успешный EOF и закрытие при отзыве сессии.

Изменяемые агрегаты читаются с `FOR UPDATE` внутри callback-транзакции; обычные Load
не блокируют записи. Общего advisory lock нет. Для согласования с прекращением
сотрудничества обычные команды берут совместимую `FOR SHARE` на координатора,
а изменения Cooperation/приглашений — `FOR UPDATE` на него перед изменением связи.
Разные мероприятия/поощрения одного координатора могут изменяться параллельно;
прекращение сотрудничества временно ждёт и задерживает записи этого координатора.
Заказ блокируется после своего поощрения, кошельки нескольких участников — по возрастанию ID.
Чат блокирует своё мероприятие перед записью, общего mutex на все чаты нет.
Списки для демо фильтруются в памяти перед пагинацией; геометрия проверяется без PostGIS.
Для нескольких экземпляров потребуются общее файловое хранилище и пересмотр синхронизации чата.
Локальная демонстрация не требует DaData для уже сохранённых точек и справочника,
но первый вход требует доступной Flida. Реальных платежей и призов нет.
