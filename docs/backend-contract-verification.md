# Проверка backend по контрактам

Проверяемая версия: текущие `proto/*/v1/*_service.proto`, `domain-design.md` и решения пользователя
от 17 октября 2026 года. Только backend; браузерные формы и реальные внешние аккаунты
не входят в утверждение о выполнении серверных контрактов.

## Воспроизводимый прогон

Из `backend`, на доступной PostgreSQL:

```sh
INTEGRATION_POSTGRESQL_DSN="$POSTGRESQL_DSN" go test -count=1 -tags=integration ./integration
```

Каждый сценарий создаёт собственную схему и удаляет её после завершения. Рабочие таблицы
не используются. Goose применяется только для подготовки этих тестовых схем;
сервер миграций не запускает. На пустой схеме проверяются Up, Down до нуля,
повторный Up и повторный вызов без неприменённых миграций.

`contracts_test.go` читает актуальные proto и проверяет, что каждый RPC был вызван.
Сам факт вызова не заменяет проверку поведения: ниже указаны сценарии с утверждениями
о результате, правах, сохранённом состоянии и ошибках. Вход проходит через настоящие
RPC, serde, app, агрегаты и pgx/Squirrel-репозитории.

## Архитектура и стиль

Сборка проверяется через `go build ./...`, стиль — через golangci-lint с тегом integration,
контракты — через buf lint. При проверке исходников подтверждены:

- `api → app → domain`; адаптеры и SQL в infra, сборка в `cmd/hahaton`.
- Сервисы app не импортируют и не вызывают другие сервисы; регистрация/вход оркестрируются RPC.
- Команды меняют агрегаты; конструкторы агрегатов и команд не валидируют модели.
- Отдельные доменные модели, приватные поля, конструкторы с Validate, геттеры и receiver `x`.
- Config, как во Flida, имеет публичные поля с env/envPrefix; ParseOptions разбирает ключи,
  точки входа вызывают env.ParseWithOptions напрямую. Промежуточного environment и геттеров Config нет.
- Callback репозитория передаёт context pgx transaction, вложенные обращения используют его.
- Схема без бизнес-CHECK; одна таблица на миграцию; миграции запускаются вручную.
- Нет ES, CQRS, service_session, SessionKey, closedAt, ролей в сессии, Origin-проверки в Authentication,
  логирования/трассировки приложения. Admin RPC на общем listener защищены Bearer-токеном.
- Короткие сигнатуры/вызовы занимают одну строку до 120 символов. Длинные параметры и поля структур
  оформляются отдельно; сгенерированный код не форматируется вручную.

## Границы утверждения

Проверки не требуют живых Flida/DaData и не доказывают доступность конкретного внешнего аккаунта
или квоты. Это проверяется при заполнении окружения. Полный браузерный путь, формы загрузки,
переключение режима и презентация относятся к фронту/подготовке защиты.

CSV загружается отдельно; источник не заменён несколькими учебными городами. Реальный полный CSV
из открытого справочника ранее импортирован и прочитан (1103 записи). Полигоны населённых пунктов
загружаются отдельным файлом; при их отсутствии API честно предлагает выбрать радиус.

По решению пользователя это демо без специальной защиты от редких параллельных команд:
проверки двух конкурентных покупок/одобрений не входят в утверждение о готовности. Атомарность
одной бизнес-команды обеспечивается PostgreSQL. Перед пилотом с нагрузкой потребуются
согласованные блокировки и общее файловое хранилище.

После упорядочивания proto номера всех 348 полей в 118 сообщениях идут подряд с 1;
варианты oneof используют общую нумерацию сообщения. Go-код перегенерирован.
TypeScript и исходники фронта в этом изменении не обновляются по решению пользователя;
их генерация и подключение к обновлённому контракту выполняются отдельно.

Проверка моделей дополнена прохождением через RPC и PostgreSQL: канонизация почты
Gmail/Yandex/Proton/Apple, хранение 29 февраля, запрет неполной/невозможной/будущей
даты и недопустимых контактов при регистрации, повторный вход с неполными claims.
Истории заявок и операции кошелька проходят существующие сценарии после переноса
хранения под репозитории агрегатов и типизации составных значений.

Runtime-сценарий дополнительно проверяет CORS двух произвольных origins для пользовательских
и административных RPC на общем listener: preflight без сессии/API key, заголовки Connect/gRPC-Web/Authorization,
доступность RPC-ошибок браузеру, сохранение аутентификации обычных запросов,
открытие/закрытие сессии и cookie SameSite=None; Secure; HttpOnly.

После типизации app DTO проверяются прежние лимиты городов, создание координатора
и мероприятия с фотографией, сохранение пропущенной и очистка переданной фотографии,
невалидный путь, отсутствие файла и запрет использования чужого изображения.
Структурная проверка 118 файлов app подтверждает отсутствие импортов других сервисов,
публичных полей и смешанных receivers, а также вызов r.Validate в начале всех 59 сервисов.


Проверка API и serde дополнена `api_conversions_test.go`: HTTP-ошибки содержат
декодируемый BadRequest с корректными путями id/counterpart/полей oneof/results[0].
Все шесть требований мероприятия сохраняют значение после RPC → модель → БД → RPC.
UNSPECIFIED, неизвестные enum, повтор требований и некорректный outcome отклоняются.
Весь прогон включает десять сценариев и проверяет вызовы всех 58 RPC.
Сборка и golangci-lint с тегом integration проходят без замечаний.

В interceptor пути RPC берутся из сгенерированных Procedure, без строкового дублирования.
В 12 PostgreSQL-репозиториях имена колонок вынесены в константы Column, включая
COALESCE, порядок сообщений и UPSERT каталога городов; поведение проверено тем же прогоном.


`infrastructure_test.go` проверяет общий PostgreSQL-клиент: вложенный Modify кошелька
и вставка операции видны через Query/QueryRow в том же ctx. Ошибка внешнего callback
откатывает кошелёк, журнал и мероприятие; успешный вызов фиксирует всё вместе.
Проверены сохранение отсутствующих Wallet/Event с доменным NotFound и отображение
дубликата Event в AlreadyExists. `geo_images_test.go` дополнительно проверяет ошибочный
JSON DaData, отсутствие suggestions и неверную форму списка как Unavailable.
Полный прогон: десять сценариев, все 58 RPC.

Проверены 34 транзакционных callback app и вызываемые ими приватные методы:
обращений к Flida, DaData и файловому хранилищу внутри нет. Проверки фотографий
для четырёх Update выполняются до Modify. Репозитории не выполняют HTTP/file I/O;
шифрование приглашений/сообщений — локальные вычисления.


## Интеграционные suites репозиториев

Отдельный набор находится в `backend/tests/integration/repository`: 12 suites и
114 тестовых сценариев. Используются версии библиотек Flida — testify 1.11.1 и
Testcontainers 0.44.0; PostgreSQL 17 запускается на случайном порту через общий
`pkg/testcontainers/postgresql`, схема создаётся Goose. Набор не требует DSN,
не использует рабочую БД и не обращается к Flida/DaData.

Проверяются все публичные операции репозиториев: сохранение/чтение агрегатов,
списки, отсутствие записей, дубликаты, callback commit/rollback, замена/удаление
сессии, составной ключ сотрудничества, поиск по iss/sub, наличие профиля координатора,
удаление приглашения, nullable-данные, фотографии и их очистка, результаты участия,
счётчики поощрений, статусы/причины отмены, истории изменений и три типа операций кошелька.
Чат проверяется на порядок/изоляцию сообщений и откат вставки; для приглашений и
сообщений дополнительно подтверждено шифрование хранимого значения.

Покрытие statements всех PostgreSQL-репозиториев суммарно — 80,4%.
Тесты не моделируют редкие гонки параллельных запросов или все отказы драйвера.
Форматирование и golangci-lint применяются к тестам по тем же правилам проекта.

Команда из backend:



## E2E на отдельном процессе приложения

Набор `backend/tests/e2e/rpc` использует generated Connect clients и testify/suite по образцу
Flida. PostgreSQL 17 поднимается в Testcontainers с миграциями Goose; `hahaton.Run` запускается
дочерним процессом тестового бинарника с настоящим общим HTTPS listener для пользовательского и административного API.
Подменяются только внешние Flida OIDC/JWKS и DaData. Подпись токена и проверка TLS реальны.
В рабочую БД тесты не обращаются. Прямой SQL используется только для подготовки прошедшего
времени мероприятия; начисления, покупки и проверки результатов выполняются RPC.

Успешные вызовы сверяются с protobuf descriptors: все 58 RPC обязательны в полном прогоне.
Все 50 RPC авторизованного участника дополнительно проверяются без cookie, с анонимной,
закрытой и поддельной сессией. Проверяются admin key на общем listener, чужие ресурсы,
InvalidArgument/NotFound details, пагинация, optional-поля, подпись/claims ID token,
права на изображения, начисления/списания/возвраты, история чата и отзыв открытого стрима.

Десять параллельных сценариев в `concurrency_test.go`:

- Два одобрения на последнее место.
- Два покупателя последнего поощрения и покупки разных поощрений на один баланс.
- Повторные CompleteEvent и CreateRewardOrder с одним ключом.
- TerminateCooperation одновременно с RequestParticipation и CreateRewardOrder.
- ApproveParticipation одновременно с CancelParticipation.
- CancelEvent одновременно с RequestParticipation.
- IssueRewardOrder одновременно с CancelRewardOrder.
- ApproveCooperation одновременно с RejectCooperation.
- TerminateCooperation одновременно с CompleteEvent.
- Два CompleteEvent разных координаторов с несколькими общими волонтёрами в обратном порядке.

Тесты выявили продажу последнего поощрения двум покупателям, ошибку параллельного
повторного начисления и сохранение PENDING-заказа после прекращения сотрудничества.
Исправление: FOR UPDATE изменяемых агрегатов и проверка повторов CompleteEvent/CreateRewardOrder
внутри транзакции. Обычные команды берут FOR SHARE координатора, изменение сотрудничества
и приглашений — FOR UPDATE на него перед каскадом. Заказы блокируют поощрение до заказа;
кошельки в пакетных операциях захватываются по возрастанию ID. Общий advisory lock и
mutex всех чатов удалены. Взаимная блокировка двух пакетных начислений воспроизведена
отдельным e2e и исправлена единым порядком кошельков.

Интеграционный `event/postgresql/concurrency_test.go` подтверждает параллельное изменение
разных мероприятий одного координатора: с прежним advisory lock он падал по таймауту,
после перехода на строки проходит. Чтения Load не берут блокировки строк.

```sh
go test -tags=e2e -count=1 -v ./tests/e2e/rpc
go test -race -tags=e2e -count=1 ./tests/e2e/rpc
```
