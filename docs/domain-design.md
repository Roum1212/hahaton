# Цифровой волонтёр Обнинска: модель, контракты и план реализации

Дата: 16 октября 2026 года. Этот документ и [словарь](../CONTEXT.md) используются
при будущей реализации. Последние явные решения пользователя имеют приоритет.

Прикладная реализация backend и frontend пока не выполняется.
Контракты приведены к единому Flida-входу, общему user_id и проверке профиля
координатора; Go/TS-код генерируется из этих контрактов. Локальных login/password нет.
Модель покрывает обычные сценарии и обязательные ограничения MVP.
Защита от редких задержанных команд через версии и клиентские идентификаторы
периодов чата исключена по решению пользователя.

## 1. Цель и границы MVP

Учебные данные, не менее трёх мероприятий и трёх поощрений, без реальных платежей.
Сценарий защиты: выбор мероприятия → заявка → ручное принятие → после ends_at
подтверждение 180 минут → операция +30 коинов → поощрение за 20 → баланс 10.
Повтор завершения не создаёт второго начисления.

Монолит, PostgreSQL, обычное хранение текущего состояния. Event sourcing не используется.
От Flida берутся стиль proto, подход к cookie-сессии и библиотека ошибок Connect RPC.
Агрегат не означает отдельный процесс. Неограниченные журналы хранятся отдельно,
а не загружаются в память вместе с агрегатом.

Магазинов, членств, общих карточек разных координаторов, архивации поощрений,
автоматического принятия заявок, ручного ввода коинов и отложенного начисления нет.
Рейтинги, достижения, экспорт, геолокационная проверка присутствия — вне MVP.

## 2. Агрегаты и записи

| Агрегат | Владеет | Основные инварианты |
| --- | --- | --- |
| Coordinator | Дополнительный профиль участника, описание, аватар и настройки | Создаётся разработчиками для существующего Volunteer; тот же ID; ФИО общее. |
| Volunteer | Профиль, привязка iss/sub | Одна запись на проверенные iss + sub; контакты только из первой регистрации. |
| Cooperation | Состояние единственной пары координатор/волонтёр, история переходов | Доступ только при ACTIVE; повторная заявка после отказа ограничена retry_after. |
| CooperationInvitation | Владелец, секрет приглашения, необязательный срок | Многоразовое; отзыв/истечение не прекращают существующее сотрудничество. |
| Event | Создатель, содержание, точка, расписание, лимит и состояние | Один владелец; нет правок при PENDING/APPROVED; завершение один раз. |
| Participation | Единственная заявка пары мероприятие/волонтёр, история и результат | Стабильный ID; REJECTED окончателен; начисление только в общем CompleteEvent. |
| Wallet | Общий баланс и подтверждённые минуты волонтёра | Баланс >= 0; операция и изменение итогов атомарны; уникальное основание. |
| Reward | Карточка, единственный владелец, цена и количество | Цена > 0; резерв + выданное <= quantity_limit. |
| RewardOrder | Одна единица, снимки условий, резерв, выдача/возврат | Списание один раз; возврат только до выдачи; ISSUED неизменяем. |
| EventChat | Чат одного события, последовательность сообщений и доступ | Пишут только текущие участники; после завершения только чтение. |
| Session | Срок, отзыв, анонимное состояние либо user_id участника | Общий ID для обоих профилей; режим кабинета в сессии не хранится. |

VolunteerOperation — неизменяемая запись журнала Wallet, ParticipationChange —
запись аудита заявки, EventChatMessage — сообщение. Это не отдельные агрегаты.
Город — справочная запись; точка, область поиска и результат участия — значения.
Границы агрегатов логические: команды приложения могут затрагивать несколько
агрегатов в одной транзакции PostgreSQL для согласованности MVP.

## 3. Идентичность, профиль и доступ

Каждый участник сначала регистрируется как волонтёр через Flida ID token.
Сервер проверяет подпись, iss, aud, срок
и применимые требования OIDC. Идентичность — (iss, sub), не aud.
Первый успешный AuthenticateSession создаёт Volunteer и Wallet с нулевыми итогами.
Обязательны имя, фамилия, полная дата рождения, email и телефон; отчество необязательно.
Повторный вход не перезаписывает локальный профиль. Email сам по себе не объединяет аккаунты.

Для выдачи координаторского доступа участник сообщает разработчикам ID, телефон
или почту. AdminService.FindVolunteers по точному ID/телефону/почте возвращает
страницу совпадений с ФИО, контактами и признаком наличия Coordinator.
Поиск требует служебной аутентификации и сам по себе прав не выдаёт.
CreateCoordinator принимает
конкретный volunteer_id и создаёт Coordinator с тем же внутренним ID.
Телефон и почта служат поиску, а привязка создаётся к найденному ID.
Общий внутренний ID не подменяет внешнюю привязку (iss, sub).
Volunteer и Coordinator остаются двумя агрегатами, с отдельными записями и поведением.
Создать Coordinator без существующего Volunteer нельзя.

ФИО общее, источником является Volunteer. Имя координатора в ответах выводится
из этого профиля; отдельно менять ФИО в UpdateCoordinator нельзя.
Описание, avatar_url и настройки Coordinator самостоятельны.
Аватар в MVP — HTTPS URL; отдельного файлового хранилища/загрузки контракт не требует.
Локальных логинов/паролей, их смены и сброса для координатора больше нет.
Координаторская возможность выдаётся только разработчиками, не самим пользователем.

Волонтёр может менять имя, фамилию, отчество и дату рождения.
Телефон, почта, привязка к Flida, баланс и минуты через UpdateVolunteer не меняются.
Изменение ФИО отражается в обоих режимах; уже сохранённые снимки авторов сообщений
и операций остаются историческими снимками.

GetVolunteer возвращает полную карточку только самому волонтёру.
GetCoordinatorVolunteer — отдельная ограниченная проекция для координатора:
ФИО связанного с ним волонтёра, контакты только при ACTIVE Cooperation.
Связь для показа ФИО — существующая Cooperation, участие в своём событии
или заказ на своё поощрение; это позволяет рассмотреть заявку и читать историю.
При чтении чужого волонтёра дата рождения, общий баланс, общие минуты и чужие покупки
координатору не выдаются. Участник с профилем координатора сохраняет доступ к своей
полной карточке волонтёра и собственному кошельку.
Результаты только своих мероприятий координатор читает через ParticipationService.
После прекращения сотрудничества контакты скрываются; история своих результатов остаётся.

## 4. Сессии и interceptor

Поток клиента: OpenSession → AuthenticateSession → прикладные RPC → CloseSession.
OpenSession ставит cookie анонимной сессии. Действующая сессия не заменяется этим вызовом.
AuthenticateSession принимает внешний Flida id_token, находит или регистрирует
участника и привязывает его общий user_id к сессии. Прямого входа по ID нет.
Потерянный ответ входа можно разрешить новым входом; очереди отложенных команд
и сложный протокол повторов не проектируются.

В сессии нет coordinator_id/volunteer_id oneof и нет активной роли.
GetSession сообщает user_id и вычисляемое наличие профиля Coordinator для интерфейса.
Для участника с двумя профилями переключение режима кабинета выполняется на фронте,
без повторной авторизации и без специального RPC переключения роли.
Выбор другого человека по-прежнему требует выхода и нового входа.

В cookie находится защищённое непрозрачное значение с session_id.
Субъект, срок и признак отзыва проверяются по серверному состоянию Session.
Connect interceptor извлекает cookie, проверяет сессию и помещает проверенную
проекцию в context. Обработчик получает общий user_id из context.
Координаторские RPC дополнительно требуют существования Coordinator с этим ID;
далее проверяется владение конкретным Event/Reward или другая связь доступа.
Наличие Coordinator не разрешает управлять чужими мероприятиями и поощрениями.
Выбранный на фронте режим не выдаёт прав и не используется как доказательство роли.
Собственных access/refresh JWT приложения и хранения их в localStorage нет.
Внешний ID token Flida — только доказательство входа, не сессия приложения.

Cookie: HttpOnly, Secure, Path=/; предпочтительно один origin с фронтом.
SameSite=Lax для такого развёртывания. Если нужны разные сайты —
SameSite=None, credentials: include и точный CORS allowlist.
Проверка Origin для изменяющих браузерных RPC; служебный AdminService изолирован.
Сроки сессий задаются конфигурацией, точный expires_at возвращается клиенту.
CloseSession отзывает текущую сессию и удаляет cookie; истёкшая/отозванная сессия
даёт Unauthenticated и закрывает её стримы.

AdminService имеет отдельную служебную аутентификацию и не доступен обычной
cookie участника. Отдельный listener/маршрут не означает отдельный микросервис.
Cookie, id_token и секреты приглашений не попадают в журналы запросов.

### Области списков при общем ID

Для двойного профиля сервер не может выводить назначение общего RPC из типа сессии.
Списки принимают обязательный scope; UNSPECIFIED/неизвестное значение — InvalidArgument.

| RPC | Области выборки |
| --- | --- |
| ListEvents | CATALOG — доступные события партнёров; OWNED — свои события координатора. |
| ListRewards | CATALOG — доступные поощрения партнёров; OWNED — свои поощрения. |
| ListParticipations | MY_APPLICATIONS — свои заявки; MY_EVENTS — заявки на свои события. |
| ListCooperations | AS_VOLUNTEER — связи со своими координаторами; AS_COORDINATOR — со своими волонтёрами. |
| ListRewardOrders | MY_PURCHASES — свои покупки; INCOMING — заказы на свои поощрения. |

Координаторские области требуют наличия Coordinator. scope выбирает набор данных,
сервер независимо проверяет права, а остальные фильтры только сужают выборку.
Наличие Coordinator не меняет scope автоматически. В CATALOG событий SearchArea
обязательна, в OWNED — дополнительный необязательный фильтр.
ListMyEventChats возвращает объединение всех доступных собственных и волонтёрских
чатов без дубликатов, независимо от режима кабинета.
В чате роль автора определяется мероприятием: его владелец — координатор,
остальные допущенные участники — волонтёры.

## 5. Сотрудничество

Сотрудничество с самим собой запрещено: coordinator_id не может совпадать
с volunteer_id. Проверка одинакова для обычной заявки и принятия приглашения.
Поэтому участник не записывается на свои мероприятия и не покупает свои поощрения,
но может участвовать у других координаторов.

| Действие | Из состояния | Результат |
| --- | --- | --- |
| Обычная заявка волонтёра | Связи нет | PENDING |
| Повторная обычная заявка | REJECTED и now >= retry_after | PENDING той же пары |
| Повторная обычная заявка | TERMINATED | PENDING той же пары |
| Принятие координатором | PENDING | ACTIVE |
| Отказ координатора | PENDING | REJECTED, retry_after = now + текущая настройка N |
| Действующее приглашение | Нет / PENDING / REJECTED / TERMINATED | ACTIVE |
| Действующее приглашение | ACTIVE | Без изменений |
| Прекращение любой стороной | ACTIVE | TERMINATED |

Обычная заявка при PENDING/ACTIVE — AlreadyExists; до retry_after —
FailedPrecondition. Настройка N неотрицательна, 0 допускает немедленную повторную заявку.
Изменение N не пересчитывает уже зафиксированный retry_after.
Приглашение обходит этот период: отказ не является баном.

Ссылка многоразовая, токен непредсказуем, QR содержит ту же ссылку.
invitation_url находится внутри CooperationInvitation и возвращается владельцу
при создании и в ListCooperationInvitations. После перезагрузки кабинета координатор
может снова скопировать ту же ссылку или показать QR. Ссылки чужих координаторов
не раскрываются; в логах секретов нет. Отдельного Get-приглашения для этого не требуется.
Для повторной выдачи ссылки токен хранится в зашифрованном виде: одного хеша
недостаточно, чтобы восстановить первоначальный invitation_url.
Срок необязателен, при наличии действует только при now < expires_at.
Открытие URL не меняет данные: волонтёр явно вызывает AcceptCooperationInvitation.

Прекращение в одной транзакции:
- сохраняет Cooperation и историю;
- отменяет все PENDING/APPROVED участия пары, даже после начала мероприятия;
- освобождает места и закрывает доступ ко всем чатам координатора;
- отменяет PENDING заказы с возвратом исходной цены и освобождением резервов;
- сохраняет CONFIRMED/NOT_ATTENDED, уже начисленное, все операции и ISSUED заказы.

Новое сотрудничество не восстанавливает заявки/заказы/старую переписку автоматически.
Постоянный бан в MVP отсутствует.

## 6. Мероприятие и заявка

Мероприятие сразу PUBLISHED. Единственный неизменяемый владелец — его создатель.
Название непустое; точка обязательна; starts_at в будущем при создании/редактировании;
ends_at > starts_at, плановая длительность кратна 1800 секундам.
Требования к кандидатам декларативные, проверяются координатором вручную.
Строковое location — пояснение к точке, а не географический фильтр.

Любые правки разрешены только до starts_at, пока нет PENDING/APPROVED.
При правке проверяется весь итоговый интервал, даже если изменена одна дата:
начало в будущем, окончание позже начала, длительность кратна 1800 секундам.
Некорректный интервал — InvalidArgument; запрет правок по состоянию — FailedPrecondition.
Только исторические REJECTED/CANCELLED записи правки не блокируют.
Отмена разрешена только до starts_at; завершение только now >= ends_at.
CANCELLED и COMPLETED конечны. Наступление времени само по себе не меняет статус.

ListEvents поддерживает отдельные интервалы starts_at_from/starts_at_to и
ends_at_from/ends_at_to: нижние границы включаются, верхние исключаются.
Все заданные фильтры применяются вместе до пагинации и подсчёта total_count.
Предстоящие события выбираются по starts_at_from = now; уже закончившиеся по времени —
по ends_at_to = now, включая PUBLISHED без подведённых итогов. COMPLETED означает
фиксацию результатов, а не просто наступление ends_at.

Одна пара (event_id, volunteer_id) — одна сохраняемая Participation.
Новая заявка всегда PENDING. Подать её можно при ACTIVE Cooperation до начала,
в том числе при полностью занятом лимите. Это резерв, места он не занимает.
Ручное одобрение переводит PENDING → APPROVED при свободном месте;
автоматического продвижения или гарантии FIFO нет.

| Переход Participation | Кто / условие |
| --- | --- |
| Нет → PENDING | Волонтёр, ACTIVE Cooperation, PUBLISHED, now < starts_at |
| PENDING → APPROVED | Создатель, те же условия и свободное место |
| PENDING → REJECTED | Создатель, пока Event PUBLISHED; необязательная приватная причина |
| PENDING/APPROVED → CANCELLED | Волонтёр до начала; место освобождается |
| CANCELLED → PENDING | Волонтёр до начала при ACTIVE Cooperation и PUBLISHED |
| PENDING/APPROVED → CANCELLED | Автоматически при отмене Event или прекращении Cooperation |
| APPROVED → CONFIRMED/NOT_ATTENDED | Только общий CompleteEvent |
| PENDING → CLOSED | Автоматически при CompleteEvent, без начисления и отметки неявки |

REJECTED окончателен: повторная заявка на это мероприятие запрещена.
Восстановление CANCELLED не возвращает старое одобрение и место.
Причину отказа видят только адресат и создатель мероприятия.
История ParticipationChange не удаляется. cancellation_reason используется
только в CANCELLED; при восстановлении очищается, прежняя причина остаётся в аудите.

Волонтёр видит только свои заявки, координатор — заявки своих мероприятий.
Сохранённая собственная заявка позволяет читать историческую карточку Event
после прекращения связи; права на каталог, новую запись и чат из этого не следуют.

## 7. Завершение, часы и кошелёк

Фронт загружает всех APPROVED участников с пагинацией, заполняет каждого,
показывает итоговую проверку и вызывает CompleteEvent.
На каждое текущее APPROVED участие нужна ровно одна строка:
- confirmed_minutes: положительное кратное 30, допускается больше плановой длительности;
- absent: true, часов и коинов нет.

Сервер считает коины: confirmed_minutes / 30 * 5. Нельзя передать отдельную сумму коинов.
Нет строки, есть лишняя/повторная строка, неверные минуты — вся команда отклоняется.
Состав проверяется по текущему состоянию в транзакции, без expected_version от клиента.

Одна транзакция CompleteEvent фиксирует COMPLETED, результаты, CLOSED для PENDING,
неизменяемые операции и обновлённые Wallet. Успешный ответ означает, что итоги уже доступны.
Асинхронного начисления через outbox нет. Изменять итоги после завершения нельзя.

Для повтора одной команды CompleteEvent сохраняется request_id.
Тот же ключ/содержание возвращает исходный результат; иной payload — AlreadyExists.
Новый ключ к завершённому Event — FailedPrecondition.
Помимо этого UNIQUE по основанию начисления не позволяет начислить дважды.

Единый Wallet волонтёра позволяет потратить заработанное у А на поощрение Б
при ACTIVE Cooperation с Б. Покупки/возвраты не меняют подтверждённые минуты.
Каждая операция содержит основание, снимок названия, дельты, итоговый баланс/минуты,
время и возрастающий sequence внутри волонтёра. Прямых RPC изменения баланса нет.

## 8. Поощрение, заказ и выдача

У Reward один координатор-владелец. Карточки одинакового названия разных владельцев
независимы. Волонтёр видит действующие карточки только активных партнёров.
Цена — положительное целое число коинов. Доступный остаток =
quantity_limit - количество ISSUED - количество PENDING резервов.

Один RewardOrder — одна единица. CreateRewardOrder атомарно проверяет доступ,
актуальную цену, баланс и остаток, создаёт PENDING, резервирует единицу,
списывает цену и сохраняет REWARD_PURCHASE.
expected_price_coins защищает от покупки по новой неожиданной цене.
request_id отличает повтор одной покупки от намеренной второй покупки.

Снимки price_coins, reward_title и владелец заказа неизменяемы.
Редактирование карточки не переписывает ранее оплаченные заказы.
quantity_limit нельзя уменьшить ниже суммы выданного и зарезервированного.
Нулевой доступный остаток оставляет карточку видимой, покупка недоступна.

Координатор-владелец нажимает «Выдано»: PENDING → ISSUED, без нового списания.
Повтор выдачи ISSUED успешен без изменения учёта.
Волонтёр или владелец могут отменить PENDING: возвращается исходная цена,
освобождается резерв и добавляется REWARD_REFUND. Повтор не возвращает второй раз.
Срока автоматического истечения заказа нет.

DeleteReward скрывает карточку без архива/восстановления и в одной транзакции
отменяет ТОЛЬКО PENDING заказы с возвратом. ISSUED заказы не отменяются и не удаляются.
То же сохранение выданного действует при прекращении сотрудничества.
История всех заказов и операций сохраняется, даже если карточка удалена.
GetReward удалённой карточки — NotFound; сведения для истории берутся из снимков заказа.
Внутренний tombstone хранит владельца для проверки повторного DeleteReward.

Гонка выдачи/отмены/удаления разрешается блокировками: один допустимый переход.
Если выдача уже зафиксирована, последующее удаление карточки её не отменяет.
Если удаление зафиксировано первым, PENDING уже CANCELLED и выдача запрещена.

## 9. Чат

Чат создаётся вместе с Event, отдельной команды создания нет.
Координатор-создатель видит всю переписку; его тип автора задаёт сервер.
Волонтёр получает доступ при APPROVED и видит только сообщения после принятия,
в том числе при самом первом вступлении. Сервер запоминает нижнюю границу sequence.

| Ситуация | Волонтёр | Координатор-создатель |
| --- | --- | --- |
| PENDING / REJECTED / CANCELLED / CLOSED | Нет доступа | Доступ к своему чату |
| APPROVED при ACTIVE Cooperation, PUBLISHED | Чтение новых для него сообщений и запись | Чтение и запись |
| CONFIRMED / NOT_ATTENDED при ACTIVE Cooperation, COMPLETED | Сохранившееся чтение, без записи | Чтение, без записи |
| Прекращено сотрудничество | Нет доступа ко всем сообщениям | Сохраняет свои чаты |
| Event отменён | Заявки отменены, доступа нет | Чтение, без записи |

Неявка при завершении сама по себе не считается выходом из переписки.
Отдельной кнопки «покинуть чат» нет. Отмена участия/сотрудничества закрывает доступ
и стрим. Повторное принятие даёт новую нижнюю границу, старые сообщения не возвращаются.
access_period_id клиент не хранит и не передаёт; контроль выполняет сервер.
Фронт очищает кеш при потере доступа; уже прочитанное человеком отозвать невозможно.

GetEventChat возвращает метаданные/границу и read_only; ListMyEventChats — доступные чаты.
ListEventChatMessages выдаёт только видимую историю с фиксированным snapshot_sequence.
SubscribeEventChatMessages восстанавливается после after_sequence и продолжает live;
сервер всегда применяет текущую нижнюю границу. Авторизованная отправка возвращает текст.
Сообщения в БД шифруются, сквозного шифрования нет; ключ вне БД, текста нет в логах.
Одна последовательность фиксации сообщений исключает пропуски при подключении стрима.
При потере доступа/истечении сессии стрим закрывается, при медленном клиенте —
ResourceExhausted с возможностью перечитать сохранённую видимую историю.

После фиксации CompleteEvent открытые стримы доставляют оставшиеся доступные
сохранённые сообщения и успешно завершаются (EOF). Новый стрим завершённого чата
выдаёт доступную историю после after_sequence и тоже завершается, не ожидая новых сообщений.
После успешного EOF фронт перечитывает GetEventChat: при read_only=true отключает
отправку и не переподключает стрим. При потере прав/сессии возвращается прежняя ошибка,
а не успешный EOF. Отдельный тип события в стриме для этого не добавляется.

Для Send request_id убирает дубли обычного повтора. Если сообщение уже вне доступной
истории после нового принятия, повтор не возвращает его текст: FailedPrecondition.

## 10. География и DaData: backend и frontend

Источник адресных подсказок и координат — выбранный пользователем
[DaData suggest/address](https://dadata.ru/api/suggest/address/).
Сервер обращается к указанному endpoint:
https://suggestions.dadata.ru/suggestions/api/4_1/rs/suggest/address

### Адрес и точка мероприятия

Фронт передаёт query, from_bound, to_bound в GeoService.SuggestAddresses.
Границы представлены объектами с value, как у DaData.
Для списка count по умолчанию 10; после выбора подсказки — запрос count=1
по её fias_id, поскольку координаты могут отсутствовать в промежуточных подсказках.
Для выбора города используются city → city либо city → settlement.
Бэк добавляет API key, ограничивает поиск Россией, проверяет ввод и нормализует ответ.
Ключ DaData не передаётся в браузер.

Ответ содержит value/unrestricted_value, идентификаторы ФИАС, названия города/региона,
необязательную point и код точности qc_geo.
geo_lat/geo_lon DaData преобразуются в типизированные WGS84 координаты.
Отсутствие координат не заменяется (0, 0). При отсутствии/низкой точности фронт
предлагает поставить или уточнить маркер вручную.
Именно подтверждённую пользователем точку фронт передаёт в CreateEvent.
Выбор координат произвольной точки на карте остаётся доступен и без поиска адреса.

### Все города и выбранная область

ListCities сохраняет исходное требование получить все города России:
локальный справочник с пагинацией, query, регионом и отметкой наличия границы.
Подсказки DaData не являются полной выгрузкой справочника.
City.id — ФИАС-код города/населённого пункта; результат DaData сопоставляется по этому ID.
Фронт может использовать подсказки для быстрого выбора, а GetCity — для сведений
о доступности границы. Если справочной записи/геометрии нет — явный выбор радиуса.

Режимы SearchArea: city_id с проверенным полигоном населённого пункта либо
круг center + radius_meters. Диапазон радиуса в контракте MVP — 1–200000 метров.
Точка на границе входит в область. Городской округ не подменяет населённый пункт.
DaData даёт точку, не полигон территории: геометрии для городского режима готовятся отдельно.
Для MVP достаточно проверенной геометрии Обнинска; отсутствие геометрий других
городов явно отражается has_boundary=false, а не обещанием покрытия всей России.

Бэк: PostGIS ST_Covers для городской границы и ST_DWithin(geography) для метров,
индексы на геометрии. Доступ по ACTIVE Cooperation и пространственный фильтр
применяются ДО пагинации и total_count. Список/счётчик читаются в одном снимке.
Фронт хранит выбранную область; разрешение геолокации необязательно.
Список и маркеры используют один фильтр; страница результатов не выдаётся за все точки.
MapLibre — вариант интерфейса карты, не обязательная библиотека.

При недоступности DaData — Unavailable, при лимите — ResourceExhausted,
без пустого успешного ответа. Уже сохранённые точки, ручной маркер и локальный
справочник не требуют повторного обращения к DaData.
При демонстрации без интернета нужны заранее подготовленные точки и подложка.

Первичные источники географического подхода:
- [DaData](https://dadata.ru/api/suggest/address/) — поля, координаты и count.
- [ГАР ФНС](https://www.nalog.gov.ru/opendata/7707329152-fias/) — справочник; не готовый набор всех полигонов.
- [ST_Covers](https://postgis.net/docs/ST_Covers.html), [ST_DWithin](https://postgis.net/docs/ST_DWithin.html).

## 11. Транзакции и минимальная защита

Проверки выполняются на сервере, фронт только показывает допустимые действия.
Одна транзакция без нужной блокировки не заменяет проверку конкурентного состояния.
В PostgreSQL нужны согласованные блокировки затронутых строк и ограничения:

| Команда | Атомарная область |
| --- | --- |
| Принятие/отмена/восстановление заявки | Event + Participation + места + доступ чата |
| Правка/отмена Event | Event + текущие заявки/места/доступ |
| CompleteEvent | Event + текущие участия + Wallet/операции всех присутствовавших |
| CreateRewardOrder | Cooperation + Reward/резерв + Wallet + RewardOrder/операция |
| Выдача/отмена заказа | RewardOrder + Reward/резерв + Wallet/операция при возврате |
| DeleteReward | Reward + PENDING заказы + резервы + Wallet/возвраты |
| TerminateCooperation | Cooperation + текущие участия/места + чаты + PENDING заказы/возвраты |

Уникальны (iss, sub), Coordinator по ID существующего Volunteer, пары Cooperation
и Participation. Для Cooperation дополнительно coordinator_id != volunteer_id.
Операции уникальны по (тип, participation_id/order_id); для кошелька
coin_balance >= 0, confirmed_minutes >= 0, проверка переполнения при расчёте.
Блокировка Wallet сериализует списания; блокировка Event — занятие последнего места;
блокировка Reward — последний остаток. Проверка связи согласуется с её прекращением.
Транзакция откатывается целиком при любой ошибке.
Порядок блокировок определяется одинаково для команд, затрагивающих общие записи.

Обычная команда проверяет текущее состояние. expected_version и аналогов в API нет.
Фронт не делает отложенных автоматических повторов изменяющих состояние команд:
после неоднозначного таймаута перечитывает состояние.
Идемпотентность финансовых команд и уникальное основание начисления остаются —
это прямо требуется сценарием защиты, а не решение редких сетевых случаев.

## 12. Стиль proto и ошибки

Пакеты v1, явные json_name, отдельные Request/Response, типизированные даты,
presence для частичных обновлений. Поля группируются по смыслу,
внутри группы — по алфавиту; первичный ID, payload и служебные данные разделены.
reserved не используется по прямому решению пользователя.
Порядок полей не задаётся их номером; существующие номера сохраняются при перестановке.

Автор/владелец команды берётся из проверенной сессии. ID в запросе — адресуемый объект,
а не способ выдать себе роль. Отсутствующее поле Update не меняется;
пустая строка очищает только явно разрешённые текстовые поля.
Неизвестные enum/UNSPECIFIED в фильтрах — InvalidArgument.
Общая пагинация: limit=0 означает 20, допустимы 1–100; offset >= 0,
за пределами списка пустая страница. Исключения ListCities/SuggestAddresses описаны в proto.
total_count использует те же права/фильтры и снимок, что страница.
Между отдельными страницами каталога живые изменения могут менять состав списка.

Свои error.proto и коды ошибок не вводятся. Используется go.flida.dev/rpc-error,
как во Flida, и стандартные Google errdetails: BadRequest, ErrorInfo,
PreconditionFailure, ResourceInfo. Преобразование ошибок приложения — на RPC-уровне.
Версия зависимости и совместимость с Connect выбираются при реализации;
проверенный референс Flida: v0.0.0-20260812080407-d4a1447d88b2.

| Ситуация | Connect code |
| --- | --- |
| Неверное поле / минуты / неполный итоговый список | InvalidArgument |
| Нет действующей авторизованной сессии | Unauthenticated |
| Чужой объект / отсутствие требуемого профиля координатора | PermissionDenied |
| Неизвестный объект / удалённая карточка | NotFound |
| Повтор пары / конфликт request_id | AlreadyExists |
| Неподходящее состояние, рано завершать, нет места/остатка/баланса | FailedPrecondition |
| Цена изменилась после открытия карточки | Aborted |
| Недоступен DaData | Unavailable |
| Лимит подсказок / переполнен буфер стрима | ResourceExhausted |

В деталях ошибок не раскрываются чужие контакты, баланс, тексты чата или секреты.
Клиент использует Connect code и стандартные details, а не разбирает русский текст.
