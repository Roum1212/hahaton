# Цифровой волонтёр Обнинска: модель, контракты и план реализации

Дата: 17 октября 2026 года. Этот документ и [словарь](../CONTEXT.md) используются
при реализации. Последние явные решения пользователя имеют приоритет.

Реализованы все текущие RPC и агрегаты, клиент Flida, PostgreSQL-репозитории,
загрузка изображений, геопоиск, чат и сборка монолита с общим listener и административным токеном.
Сервисы не вызывают другие сервисы; команды меняют состояние агрегатов без ES/CQRS.
Volunteer и Wallet создаются атомарно; замена анонимной сессии — отдельная транзакция.
Конфигурация повторяет Flida: публичные Config/секции, env/envPrefix на полях,
ParseOptions для типизированных ключей, прямой env.ParseWithOptions в точках входа.
Правило приватных полей моделей к конфигурации не применяется.
Миграции применяются вручную через goose, одна таблица на файл. Сервер схему не меняет. Инструкции запуска — в backend/README.md.
Интеграция форм фронта, подготовка настоящей геометрии населённых пунктов и материалы защиты
остаются отдельной работой. Контракты используют единый Flida-вход и общий user_id,
локальных login/password нет. Защита от редких задержанных команд через версии
и клиентские идентификаторы периодов чата исключена по решению пользователя.

## 1. Цель и границы MVP

Учебные данные, не менее трёх мероприятий и трёх поощрений, без реальных платежей.
Сценарий защиты: выбор мероприятия → заявка → ручное принятие → после ends_at
подтверждение 180 минут → операция +30 коинов → поощрение за 20 → баланс 10.
Повтор завершения не создаёт второго начисления.

Монолит, PostgreSQL, обычное хранение текущего состояния. Event sourcing не используется.
От Flida берутся стиль proto, подход к cookie-сессии и библиотека ошибок Connect RPC.
Агрегат не означает отдельный процесс. Неограниченные журналы хранятся отдельно,
а не загружаются в память вместе с агрегатом.

Магазинов, членств, общих карточек разных координаторов, архивации поощрений,
автоматического принятия заявок, ручного ввода коинов и отложенного начисления нет.
Рейтинги, достижения, экспорт, геолокационная проверка присутствия — вне MVP.

## 2. Агрегаты и записи

| Агрегат | Владеет | Основные инварианты |
| --- | --- | --- |
| Coordinator | Дополнительный профиль участника, описание, аватар и настройки | Создаётся разработчиками для существующего Volunteer; тот же ID; ФИО общее. |
| Volunteer | Профиль, аватар, привязка iss/sub | Одна запись на проверенные iss + sub; контакты только из первой регистрации. |
| Cooperation | Состояние единственной пары координатор/волонтёр, история переходов | Доступ только при ACTIVE; повторная заявка после отказа ограничена retry_after. |
| CooperationInvitation | Владелец, секрет приглашения, необязательный срок | Многоразовое; отзыв/истечение не прекращают существующее сотрудничество. |
| Event | Создатель, содержание, точка, расписание, лимит и состояние | Один владелец; нет правок при PENDING/APPROVED; завершение один раз. |
| Participation | Единственная заявка пары мероприятие/волонтёр, история и результат | Стабильный ID; REJECTED окончателен; начисление только в общем CompleteEvent. |
| Wallet | Общий баланс и подтверждённые минуты волонтёра | Баланс >= 0; операция и изменение итогов атомарны; уникальное основание. |
| Reward | Карточка, изображение, единственный владелец, цена и количество | Цена > 0; резерв + выданное <= quantity_limit. |
| RewardOrder | Одна единица, снимки условий, резерв, выдача/возврат | Списание один раз; возврат только до выдачи; ISSUED неизменяем. |
| EventChat | Чат одного события, последовательность сообщений и доступ | Пишут только текущие участники; после завершения только чтение. |
| Session | Срок, отзыв, анонимное состояние либо user_id участника | Общий ID для обоих профилей; режим кабинета в сессии не хранится. |

VolunteerOperation — неизменяемая запись журнала Wallet, ParticipationChange —
запись аудита заявки, CooperationChange — запись истории сотрудничества, EventChatMessage — сообщение. Это не отдельные агрегаты.
Город — справочная запись; точка, область поиска и результат участия — значения.
Границы агрегатов логические: команды приложения могут затрагивать несколько
агрегатов в одной транзакции PostgreSQL для согласованности MVP.

## 3. Идентичность, профиль и доступ

Каждый участник сначала регистрируется как волонтёр через Flida ID token.
Сервер проверяет подпись, iss, aud, срок
и применимые требования OIDC. Идентичность — (iss, sub), не aud.
Первый успешный AuthenticateSession создаёт Volunteer и Wallet с нулевыми итогами.
Обязательны имя, фамилия, полная дата рождения, email и телефон; отчество необязательно.
Повторный вход не перезаписывает локальный профиль. Email сам по себе не объединяет аккаунты.

Проверку ID token выполняет `infra/client/flida`: OIDC discovery, ключи JWKS, RS256,
ожидаемые issuer/audience, срок, iat/nbf и применимый azp. Адрес issuer и client ID задаются
конфигурацией; клиенту передаётся HTTP-клиент с timeout. Внешний sub остаётся непрозрачной строкой.
Имя и контакты берутся из `given_name`, `family_name`, `middle_name`, `email`, `phone_number`,
дата рождения — из `date_of_birth`, как в генераторе токенов Flida.
`app/service/get-or-register-volunteer` принимает ID token, получает проверенный профиль через клиент Flida,
ищет по `(iss, sub)`
и проверяет обязательные данные только при первой регистрации. Для существующего профиля
неполные claims не мешают входу и не меняют сохранённые данные.
Сервис выполняет команды агрегатов; конструкторы агрегатов/команд предполагают валидные модели.
Агрегаты и команды принимают существующие модели целиком, без промежуточного
преобразования в строки/числа. В частности, Participation.Complete и Wallet.Accrue
получают EventResult. Participation хранит необязательный EventResult до завершения
и результат после завершения; совпадение ID результата и заявки проверяет команда
агрегата. Репозиторий восстанавливает модель из столбцов PostgreSQL до вызова
NewParticipationFromFields; конструктор агрегата не валидирует модели.
Суммы, остатки, тексты и номера последовательностей без отдельных моделей остаются
простыми значениями; EventTitle и VolunteerLimit не используются для названий наград
или товарных остатков, поскольку это другие понятия.

Модели FullName, DateOfBirth, EmailAddress, PhoneNumber проверяются своими конструкторами.
Profile принимает эти модели и Identity, а не строковые claims. Клиент Flida разбирает
внешние строки и возвращает проверенную Identity с необязательным полным Profile.
Неполный профиль запрещает первую регистрацию, но не повторный вход существующего волонтёра.
DateOfBirth перенесён из Flida: год/месяц/день, календарная проверка, минимум 1900 год,
запрет будущей даты; нулевое значение допустимо для самой модели, но не для регистрации
или изменения даты рождения. EmailAddress использует локально перенесённую логику Flida:
разбор адреса, IDNA и ICANN TLD, нормализацию домена и имени почтового ящика.
Domain, Label и Username размещены в отдельных пакетах моделей; сравнение адресов — через Equals.

В сервисах и DTO используются существующие модели, включая ImagePath и Page.
RPC разбирает строковые avatar_path/image_path в ImagePath. Нулевой ImagePath —
валидное отсутствие фотографии; Optional[ImagePath] различает пропущенное обновление
и явную очистку. Проверки владельца и существования файла выполняет app.
UploadImage собирает ImagePath из UserID и UUIDv7 без строкового промежуточного пути.
ListCities принимает Page с прежней политикой: по умолчанию 100, максимум 1000;
остальные списки сохраняют 20/100. Счётчики, scope, внешние city_id и ключи запросов
без собственных моделей остаются простыми значениями.
Частичные изменения имени и расписания объединяются с текущим агрегатом, затем
конструкторы FullName и EventSchedule создают полные валидные значения.
Каждый сервис начинает работу с Request.Validate; импорты и вызовы других app-сервисов
запрещены. Response остаётся в dto.go и содержит агрегаты/модели и необходимые метаданные.

В domain/model нет репозиториев, зависимостей от SQL, RPC или infra.
CooperationChange хранится через репозиторий Cooperation, ParticipationChange — через
Participation, Operation — через Wallet, в тех же транзакциях, что и изменения агрегатов.
История заявок использует ParticipationStatus, UserID и ActorKind; предыдущий статус
необязателен у первой записи. У системного изменения отсутствует ID участника.
Чат использует тот же ActorKind и допускает автора только координатора или волонтёра.
Операция кошелька содержит OperationType и OperationSource: либо ParticipationID для
начисления, либо RewardOrderID для покупки/возврата. Несовпадение типа и источника невалидно.
EventRequirements состоит из отдельных моделей Requirement. Простые строковые значения
(названия, тексты, внешние идентификаторы) остаются в соответствующих моделях значений.

Проверки профиля не переносятся в SQL. Миграции `00002_volunteers.sql` и `00003_wallets.sql` хранят текущие
состояния; у `(flida_issuer, flida_subject)` техническое ограничение уникальности.

Для выдачи координаторского доступа участник сообщает разработчикам ID, телефон
или почту. AdminService.FindVolunteers по точному ID/телефону/почте возвращает
страницу совпадений с ФИО, контактами и признаком наличия Coordinator.
Поиск требует служебной аутентификации и сам по себе прав не выдаёт.
CreateCoordinator принимает
конкретный volunteer_id и создаёт Coordinator с тем же внутренним ID.
Телефон и почта служат поиску, а привязка создаётся к найденному ID.
Общий внутренний ID не подменяет внешнюю привязку (iss, sub).
Volunteer и Coordinator остаются двумя агрегатами, с отдельными записями и поведением.
Создать Coordinator без существующего Volunteer нельзя.

ФИО общее, источником является Volunteer. Имя координатора в ответах выводится
из этого профиля; отдельно менять ФИО в UpdateCoordinator нельзя.
Описание, аватар и настройки Coordinator самостоятельны.
Volunteer и Coordinator могут иметь разные аватары при общем ID участника.
Изображения загружаются через ImageService; внешний URL вместо загрузки не принимается.
Правила хранения и привязки описаны в разделе 10.1.
Локальных логинов/паролей, их смены и сброса для координатора больше нет.
Координаторская возможность выдаётся только разработчиками, не самим пользователем.

Волонтёр может менять имя, фамилию, отчество, дату рождения и свой аватар.
Телефон, почта, привязка к Flida, баланс и минуты через UpdateVolunteer не меняются.
Изменение ФИО отражается в обоих режимах; уже сохранённые снимки авторов сообщений
и операций остаются историческими снимками.

GetVolunteer возвращает полную карточку только самому волонтёру.
GetCoordinatorVolunteer — отдельная ограниченная проекция для координатора:
ФИО связанного с ним волонтёра, контакты только при ACTIVE Cooperation.
Связь для показа ФИО — существующая Cooperation, участие в своём событии
или заказ на своё поощрение; это позволяет рассмотреть заявку и читать историю.
При чтении чужого волонтёра дата рождения, общий баланс, общие минуты и чужие покупки
координатору не выдаются. Участник с профилем координатора сохраняет доступ к своей
полной карточке волонтёра и собственному кошельку.
Результаты только своих мероприятий координатор читает через ParticipationService.
После прекращения сотрудничества контакты скрываются; история своих результатов остаётся.

## 4. Сессии и interceptor

Поток клиента: OpenSession → AuthenticateSession → прикладные RPC → CloseSession.
OpenSession ставит cookie анонимной сессии. Действующая сессия не заменяется этим вызовом.
OpenSession и AuthenticateSession возвращают google.protobuf.Empty и передают cookie
через Set-Cookie. Состояние кабинета клиент получает отдельным GetSession.
OpenSession, GetSession и CloseSession принимают google.protobuf.Empty; их Request в app тоже пустые.
Идентификатор не передаётся в DTO: сервисы получают текущий агрегат из context.
Open/Get не перечитывают сессию из БД после проверки в Authentication.
AuthenticateSession принимает внешний Flida id_token, находит или регистрирует
участника и привязывает его общий user_id к сессии. Прямого входа по ID нет.
После проверки входа создаётся новая авторизованная сессия с другим session_id,
а прежняя анонимная удаляется. Обе операции выполняются в одной транзакции PostgreSQL.
Для демо репозиторий предоставляет Replace с callback: открывает транзакцию через
клиент pgx, загружает старую сессию и передаёт её callback сервиса. Сервис проверяет
состояние, выполняет команды и возвращает новый агрегат. Репозиторий удаляет старый
и сохраняет новый. Unit of Work и Transactor в сервисе не используются;
Replace читает прежнюю сессию с FOR UPDATE.
Сервисы app не вызывают друг друга. Как в RPC регистрации аккаунта Flida,
последовательность собирает RPC: GetOrRegisterVolunteer, затем AuthenticateSession.
Первый сервис проверяет ID token через клиент Flida и возвращает агрегат Volunteer;
второй принимает session_id и user_id и заменяет сессию через команды агрегата.
При новом участнике репозиторий Volunteer сохраняет агрегат, затем вызывает callback
записи открытого Wallet в одной транзакции. Замена сессии выполняется отдельной транзакцией.
Ошибка создания Wallet откатывает профиль. Ошибка замены сессии сохраняет уже созданный профиль
и кошелёк; повторный вход найдёт их и повторит авторизацию без повторной регистрации.
Client.InTx передаёт транзакцию через context, вложенный вызов использует её без отдельного commit/savepoint.
Для параллельной работы Modify/Replace загружают изменяемый агрегат с FOR UPDATE.
Публичные Load остаются обычными SELECT. Общего advisory lock в InTx нет.
Сначала берётся FOR SHARE координатора для Event/Reward/RewardOrder/чата;
изменение Cooperation/приглашения берёт FOR UPDATE на него перед каскадом.
Совместимые shared-блокировки позволяют независимо менять мероприятия/поощрения
одного координатора; прекращение сотрудничества временно задерживает его записи.
Заказы блокируют Reward до RewardOrder, чат — Event до EventChat. При изменении нескольких
кошельков порядок единый: volunteer_id по возрастанию. Общий mutex чатов не используется.
Проверки повторов CompleteEvent и CreateRewardOrder выполняются внутри этой транзакции.
Существующая анонимная запись не авторизуется на месте. Отдельного SessionKey нет.
Потерянный ответ входа можно разрешить новым входом; очереди отложенных команд
и сложный протокол повторов не проектируются.

В сессии нет coordinator_id/volunteer_id oneof и нет активной роли.
GetSession сообщает user_id и вычисляемое наличие профиля Coordinator для интерфейса.
Для участника с двумя профилями переключение режима кабинета выполняется на фронте,
без повторной авторизации и без специального RPC переключения роли.
Выбор другого человека по-прежнему требует выхода и нового входа.

В cookie находится защищённое непрозрачное значение с session_id.
PASETO проверяет iat/nbf/exp относительно текущего времени на каждом запросе.
Интерфейсы token.Service/Encryptor/Decryptor, EncryptedToken и общий PASETO-адаптер
перенесены из Flida в internal/pkg/token; внешний пакет Flida с этой логикой не импортируется.
Сервисы Open/Authenticate возвращают EncryptedToken, RPC устанавливает его String() в cookie.
Authentication создаёт EncryptedToken из cookie и расшифровывает типизированный session_token.Token.
Последний хранит ID и даты сессии; общие поля user_id и наличие Coordinator по-прежнему читаются из БД.
Наличие записи, субъект и срок проверяются по серверному состоянию Session.
Отзыв означает удаление записи; закрытые сессии в БД не сохраняются.
Authentication.Authenticate извлекает cookie, проверяет сессию и возвращает агрегат Session.
authn.NewMiddleware помещает его в context через authn.SetInfo; RPC получает его через
session_context.GetSession/authn.GetInfo и читает общий user_id через геттер.
Отдельной проекции Session и CQRS нет. Наличие Coordinator вычисляется сервисом
GetSession и передаётся в DTO ответа, не сохраняется в Session.
Interceptor находится в internal/pkg/session/authentication/interceptor;
подключается через authn.NewMiddleware(authentication.Authenticate).Wrap(router), как во Flida.
Connect-обёртки WrapUnary/WrapStreamingHandler не используются.
Для текущих RPC режимы доступа явно перечислены в authModeByProcedure; новые RPC добавляются туда
при реализации. Неизвестные методы и служебные Admin RPC не пропускаются на клиентский listener.
Режим authModeAuthenticated проверяет отсутствие анонимности только в Authentication.
Без подходящей сессии Authentication возвращает nil info, а защищённый RPC проверяет
только наличие сессии в context и возвращает Unauthenticated, как во Flida.
Ошибка PostgreSQL возвращает Internal, а не маскируется под отсутствие входа.
Пакет cookie содержит только имя; RPC используют cookies.Service напрямую.
Шифрование выполняют сервисы приложения, в JSON-ответ значение сессии не попадает.
Проверка Origin в сессионном interceptor не выполняется.
Координаторские RPC дополнительно требуют существования Coordinator с этим ID;
далее проверяется владение конкретным Event/Reward или другая связь доступа.
Наличие Coordinator не разрешает управлять чужими мероприятиями и поощрениями.
Выбранный на фронте режим не выдаёт прав и не используется как доказательство роли.
Собственных access/refresh JWT приложения и хранения их в localStorage нет.
Внешний ID token Flida — только доказательство входа, не сессия приложения.

Cookie: HttpOnly, Secure, Path=/, SameSite=None; фронт использует credentials: include.
CORS на общем listener разрешает любой origin: AllowOriginFunc возвращает true,
Access-Control-Allow-Origin отражает origin запроса, Allow-Credentials=true.
Буквальный `*` в ответе не используется, поскольку с credentials браузер его не принимает.
Как во Flida, применяются github.com/rs/cors и списки методов/заголовков из connectrpc.com/cors;
Authorization дополнительно разрешён для служебных запросов. Preflight обрабатывается
до аутентификации; обычные запросы по-прежнему проходят сессионную или служебную проверку.
Служебный AdminService изолирован; проверки Origin в сессионном слое нет.
Сроки сессий задаются конфигурацией, точный expires_at возвращается клиенту.
CloseSession удаляет текущую сессию из PostgreSQL и удаляет cookie;
повторное удаление успешно. Истёкшая или удалённая сессия
даёт Unauthenticated при следующем запросе или открытии стрима.
В сессионном Authentication нет фонового опроса БД. Чат-сервис отдельно проверяет
сессию открытого стрима каждые 500 мс и закрывает его при истечении/отзыве,
как требует контракт EventChatService.

AdminService имеет отдельную служебную аутентификацию и не доступен обычной
cookie участника. Отдельный listener/маршрут не означает отдельный микросервис.
Cookie, id_token и секреты приглашений не попадают в журналы запросов.

### Области списков при общем ID

Для двойного профиля сервер не может выводить назначение общего RPC из типа сессии.
Списки принимают обязательный scope; UNSPECIFIED/неизвестное значение — InvalidArgument.

| RPC | Области выборки |
| --- | --- |
| ListEvents | CATALOG — доступные события партнёров; OWNED — свои события координатора. |
| ListRewards | CATALOG — доступные поощрения партнёров; OWNED — свои поощрения. |
| ListParticipations | MY_APPLICATIONS — свои заявки; MY_EVENTS — заявки на свои события. |
| ListCooperations | AS_VOLUNTEER — связи со своими координаторами; AS_COORDINATOR — со своими волонтёрами. |
| ListRewardOrders | MY_PURCHASES — свои покупки; INCOMING — заказы на свои поощрения. |

Координаторские области требуют наличия Coordinator. scope выбирает набор данных,
сервер независимо проверяет права, а остальные фильтры только сужают выборку.
Наличие Coordinator не меняет scope автоматически. В CATALOG событий SearchArea
обязательна, в OWNED — дополнительный необязательный фильтр.
ListMyEventChats возвращает объединение всех доступных собственных и волонтёрских
чатов без дубликатов, независимо от режима кабинета.
В чате роль автора определяется мероприятием: его владелец — координатор,
остальные допущенные участники — волонтёры.

## 5. Сотрудничество

Сотрудничество с самим собой запрещено: coordinator_id не может совпадать
с volunteer_id. Проверка одинакова для обычной заявки и принятия приглашения.
Поэтому участник не записывается на свои мероприятия и не покупает свои поощрения,
но может участвовать у других координаторов.

| Действие | Из состояния | Результат |
| --- | --- | --- |
| Обычная заявка волонтёра | Связи нет | PENDING |
| Повторная обычная заявка | REJECTED и now >= retry_after | PENDING той же пары |
| Повторная обычная заявка | TERMINATED | PENDING той же пары |
| Принятие координатором | PENDING | ACTIVE |
| Отказ координатора | PENDING | REJECTED, retry_after = now + текущая настройка N |
| Действующее приглашение | Нет / PENDING / REJECTED / TERMINATED | ACTIVE |
| Действующее приглашение | ACTIVE | Без изменений |
| Прекращение любой стороной | ACTIVE | TERMINATED |

Обычная заявка при PENDING/ACTIVE — AlreadyExists; до retry_after —
FailedPrecondition. Настройка N неотрицательна, 0 допускает немедленную повторную заявку.
Изменение N не пересчитывает уже зафиксированный retry_after.
Приглашение обходит этот период: отказ не является баном.

Ссылка многоразовая, токен непредсказуем, QR содержит ту же ссылку.
invitation_url находится внутри CooperationInvitation и возвращается владельцу
при создании и в ListCooperationInvitations. После перезагрузки кабинета координатор
может снова скопировать ту же ссылку или показать QR. Ссылки чужих координаторов
не раскрываются; в логах секретов нет. Отдельного Get-приглашения для этого не требуется.
Для повторной выдачи ссылки токен хранится в зашифрованном виде: одного хеша
недостаточно, чтобы восстановить первоначальный invitation_url.
Срок необязателен, при наличии действует только при now < expires_at.
Открытие URL не меняет данные: волонтёр явно вызывает AcceptCooperationInvitation.

Прекращение в одной транзакции:
- сохраняет Cooperation и историю;
- отменяет все PENDING/APPROVED участия пары, даже после начала мероприятия;
- освобождает места и закрывает доступ ко всем чатам координатора;
- отменяет PENDING заказы с возвратом исходной цены и освобождением резервов;
- сохраняет CONFIRMED/NOT_ATTENDED, уже начисленное, все операции и ISSUED заказы.

Новое сотрудничество не восстанавливает заявки/заказы/старую переписку автоматически.
Постоянный бан в MVP отсутствует.

## 6. Мероприятие и заявка

Мероприятие сразу PUBLISHED. Единственный неизменяемый владелец — его создатель.
Название непустое; точка обязательна; starts_at в будущем при создании/редактировании;
ends_at > starts_at, плановая длительность кратна 1800 секундам.
Требования к кандидатам декларативные, проверяются координатором вручную.
Строковое location — пояснение к точке, а не географический фильтр.
У мероприятия одна необязательная фотография: image_path из UploadImage при CreateEvent/UpdateEvent,
вычисляемый image_url при чтении. Файл принадлежит создавшему мероприятие координатору.
Отсутствующее поле при обновлении сохраняет фотографию, пустая строка убирает её.

Любые правки, включая фотографию, разрешены только до starts_at, пока нет PENDING/APPROVED.
При правке проверяется весь итоговый интервал, даже если изменена одна дата:
начало в будущем, окончание позже начала, длительность кратна 1800 секундам.
Некорректный интервал — InvalidArgument; запрет правок по состоянию — FailedPrecondition.
Только исторические REJECTED/CANCELLED записи правки не блокируют.
Отмена разрешена только до starts_at; завершение только now >= ends_at.
CANCELLED и COMPLETED конечны. Наступление времени само по себе не меняет статус.

ListEvents поддерживает отдельные интервалы starts_at_from/starts_at_to и
ends_at_from/ends_at_to: нижние границы включаются, верхние исключаются.
Все заданные фильтры применяются вместе до пагинации и подсчёта total_count.
Предстоящие события выбираются по starts_at_from = now; уже закончившиеся по времени —
по ends_at_to = now, включая PUBLISHED без подведённых итогов. COMPLETED означает
фиксацию результатов, а не просто наступление ends_at.

Одна пара (event_id, volunteer_id) — одна сохраняемая Participation.
Новая заявка всегда PENDING. Подать её можно при ACTIVE Cooperation до начала,
в том числе при полностью занятом лимите. Это резерв, места он не занимает.
Ручное одобрение переводит PENDING → APPROVED при свободном месте;
автоматического продвижения или гарантии FIFO нет.

| Переход Participation | Кто / условие |
| --- | --- |
| Нет → PENDING | Волонтёр, ACTIVE Cooperation, PUBLISHED, now < starts_at |
| PENDING → APPROVED | Создатель, те же условия и свободное место |
| PENDING/APPROVED → REJECTED | Создатель, пока Event PUBLISHED; необязательная приватная причина |
| PENDING/APPROVED → CANCELLED | Волонтёр до начала; место освобождается |
| CANCELLED → PENDING | Волонтёр до начала при ACTIVE Cooperation и PUBLISHED |
| PENDING/APPROVED → CANCELLED | Автоматически при отмене Event или прекращении Cooperation |
| APPROVED → CONFIRMED/NOT_ATTENDED | Только общий CompleteEvent |
| PENDING → CLOSED | Автоматически при CompleteEvent, без начисления и отметки неявки |

REJECTED окончателен: повторная заявка на это мероприятие запрещена.
RejectParticipation допускает отказ уже принятому участнику, в том числе после starts_at/ends_at,
пока Event остаётся PUBLISHED. Место освобождается, доступ к истории чата и стрим закрываются.
Коины и часы не начисляются; строка такого участника не передаётся в CompleteEvent.
После CANCELLED/COMPLETED мероприятия и для конечных статусов участия отказ запрещён.
Восстановление CANCELLED не возвращает старое одобрение и место.
Причину отказа видят только адресат и создатель мероприятия.
История ParticipationChange не удаляется. cancellation_reason используется
только в CANCELLED; при восстановлении очищается, прежняя причина остаётся в аудите.

Волонтёр видит только свои заявки, координатор — заявки своих мероприятий.
Сохранённая собственная заявка позволяет читать историческую карточку Event
после прекращения связи; права на каталог, новую запись и чат из этого не следуют.

## 7. Завершение, часы и кошелёк

Фронт загружает всех APPROVED участников с пагинацией, заполняет каждого,
показывает итоговую проверку и вызывает CompleteEvent.
На каждое текущее APPROVED участие нужна ровно одна строка:
- confirmed_minutes: положительное кратное 30, допускается больше плановой длительности;
- absent: true, часов и коинов нет.

Сервер считает коины: confirmed_minutes / 30 * 5. Нельзя передать отдельную сумму коинов.
Нет строки, есть лишняя/повторная строка, неверные минуты — вся команда отклоняется.
Состав проверяется по текущему состоянию в транзакции, без expected_version от клиента.

Одна транзакция CompleteEvent фиксирует COMPLETED, результаты, CLOSED для PENDING,
неизменяемые операции и обновлённые Wallet. Успешный ответ означает, что итоги уже доступны.
Асинхронного начисления через outbox нет. Изменять итоги после завершения нельзя.

Для повтора одной команды CompleteEvent сохраняется request_id.
Тот же ключ/содержание возвращает исходный результат; иной payload — AlreadyExists.
Новый ключ к завершённому Event — FailedPrecondition.
Помимо этого UNIQUE по основанию начисления не позволяет начислить дважды.

Единый Wallet волонтёра позволяет потратить заработанное у А на поощрение Б
при ACTIVE Cooperation с Б. Покупки/возвраты не меняют подтверждённые минуты.
Каждая операция содержит основание, снимок названия, дельты, итоговый баланс/минуты,
время и возрастающий sequence внутри волонтёра. Прямых RPC изменения баланса нет.

## 8. Поощрение, заказ и выдача

У Reward один координатор-владелец. Карточки одинакового названия разных владельцев
независимы. Волонтёр видит действующие карточки только активных партнёров.
Цена — положительное целое число коинов. Доступный остаток =
quantity_limit - количество ISSUED - количество PENDING резервов.

Один RewardOrder — одна единица. CreateRewardOrder атомарно проверяет доступ,
актуальную цену, баланс и остаток, создаёт PENDING, резервирует единицу,
списывает цену и сохраняет REWARD_PURCHASE.
expected_price_coins защищает от покупки по новой неожиданной цене.
request_id отличает повтор одной покупки от намеренной второй покупки.

Снимки price_coins, reward_title и владелец заказа неизменяемы.
Редактирование карточки не переписывает ранее оплаченные заказы.
quantity_limit нельзя уменьшить ниже суммы выданного и зарезервированного.
Нулевой доступный остаток оставляет карточку видимой, покупка недоступна.

Координатор-владелец нажимает «Выдано»: PENDING → ISSUED, без нового списания.
Повтор выдачи ISSUED успешен без изменения учёта.
Волонтёр или владелец могут отменить PENDING: возвращается исходная цена,
освобождается резерв и добавляется REWARD_REFUND. Повтор не возвращает второй раз.
Срока автоматического истечения заказа нет.

DeleteReward скрывает карточку без архива/восстановления и в одной транзакции
отменяет ТОЛЬКО PENDING заказы с возвратом. ISSUED заказы не отменяются и не удаляются.
То же сохранение выданного действует при прекращении сотрудничества.
История всех заказов и операций сохраняется, даже если карточка удалена.
GetReward удалённой карточки — NotFound; сведения для истории берутся из снимков заказа.
Внутренний tombstone хранит владельца для проверки повторного DeleteReward.

Выдача, отмена и удаление выполняют допустимый переход в транзакции.
Параллельные команды согласуются блокировками строк PostgreSQL:
координатор, затем Reward, затем RewardOrder и Wallet (раздел 11).
Если выдача уже зафиксирована, последующее удаление карточки её не отменяет.
Если удаление зафиксировано первым, PENDING уже CANCELLED и выдача запрещена.

## 9. Чат

Чат создаётся вместе с Event, отдельной команды создания нет.
Координатор-создатель видит всю переписку; его тип автора задаёт сервер.
Волонтёр получает доступ при APPROVED и видит только сообщения после принятия,
в том числе при самом первом вступлении. Сервер запоминает нижнюю границу sequence.

| Ситуация | Волонтёр | Координатор-создатель |
| --- | --- | --- |
| PENDING / REJECTED / CANCELLED / CLOSED | Нет доступа | Доступ к своему чату |
| APPROVED при ACTIVE Cooperation, PUBLISHED | Чтение новых для него сообщений и запись | Чтение и запись |
| CONFIRMED / NOT_ATTENDED при ACTIVE Cooperation, COMPLETED | Сохранившееся чтение, без записи | Чтение, без записи |
| Прекращено сотрудничество | Нет доступа ко всем сообщениям | Сохраняет свои чаты |
| Event отменён | Заявки отменены, доступа нет | Чтение, без записи |

Неявка при завершении сама по себе не считается выходом из переписки.
Отдельной кнопки «покинуть чат» нет. Отмена/отклонение участия и прекращение сотрудничества
закрывают доступ и стрим. Повторное принятие после отмены даёт новую нижнюю границу,
старые сообщения не возвращаются. Отклонённую заявку восстановить нельзя.
access_period_id клиент не хранит и не передаёт; контроль выполняет сервер.
Фронт очищает кеш при потере доступа; уже прочитанное человеком отозвать невозможно.

GetEventChat возвращает метаданные/границу и read_only; ListMyEventChats — доступные чаты.
ListEventChatMessages выдаёт только видимую историю с фиксированным snapshot_sequence.
SubscribeEventChatMessages восстанавливается после after_sequence и продолжает live;
сервер всегда применяет текущую нижнюю границу. Авторизованная отправка возвращает текст.
Сообщения в БД шифруются, сквозного шифрования нет; ключ вне БД, текста нет в логах.
Одна последовательность фиксации сообщений исключает пропуски при подключении стрима.
При потере доступа/истечении сессии стрим закрывается, при медленном клиенте —
ResourceExhausted с возможностью перечитать сохранённую видимую историю.

После фиксации CompleteEvent открытые стримы доставляют оставшиеся доступные
сохранённые сообщения и успешно завершаются (EOF). Новый стрим завершённого чата
выдаёт доступную историю после after_sequence и тоже завершается, не ожидая новых сообщений.
После успешного EOF фронт перечитывает GetEventChat: при read_only=true отключает
отправку и не переподключает стрим. При потере прав/сессии возвращается прежняя ошибка,
а не успешный EOF. Отдельный тип события в стриме для этого не добавляется.

Для Send request_id убирает дубли обычного повтора. Если сообщение уже вне доступной
истории после нового принятия, повтор не возвращает его текст: FailedPrecondition.

## 10. География и DaData: backend и frontend

Источник адресных подсказок и координат — выбранный пользователем
[DaData suggest/address](https://dadata.ru/api/suggest/address/).
Сервер обращается к указанному endpoint:
https://suggestions.dadata.ru/suggestions/api/4_1/rs/suggest/address

### Адрес и точка мероприятия

Фронт передаёт query, from_bound, to_bound в GeoService.SuggestAddresses.
Границы представлены объектами с value, как у DaData.
Для списка count по умолчанию 10; после выбора подсказки — запрос count=1
по её fias_id, поскольку координаты могут отсутствовать в промежуточных подсказках.
Для выбора города используются city → city либо city → settlement.
Бэк добавляет API key, ограничивает поиск Россией, проверяет ввод и нормализует ответ.
Ключ DaData не передаётся в браузер.

Ответ содержит value/unrestricted_value, идентификаторы ФИАС, названия города/региона,
необязательную point и код точности qc_geo.
geo_lat/geo_lon DaData преобразуются в типизированные WGS84 координаты.
Отсутствие координат не заменяется (0, 0). При отсутствии/низкой точности фронт
предлагает поставить или уточнить маркер вручную.
Именно подтверждённую пользователем точку фронт передаёт в CreateEvent.
Выбор координат произвольной точки на карте остаётся доступен и без поиска адреса.

### Поиск населённых пунктов и выбранная область

Для MVP ListCities и GetCity обращаются к DaData через серверный клиент без БД и CSV.
ListCities передаёт query с гранулярностью city → settlement, возвращает до 20 подсказок
в порядке релевантности провайдера. Пустой запрос — пустой список; offset допустим только 0.
`total_count` отражает размер ответа; `catalog_version=dadata` — источник данных.
Полная выгрузка всех городов России и локальный кеш городов в этом варианте не предусмотрены.
Старая таблица cities остаётся в БД, но не используется и не заполняется при запуске.

City.id — ФИАС-код населённого пункта. GetCity ищет его через тот же API DaData.
Регион, название и центр берутся из ответа провайдера, отсутствующие координаты не подменяются нулями.
DaData не возвращает проверенные полигоны: has_boundary=false, поиск мероприятий по city_id
возвращает FailedPrecondition. Фронт явно выбирает круг center + radius_meters;
радиус в контракте MVP — 1–200000 метров. Точка на границе круга включается.

Выбранный круг не ограничивает поиск адресных подсказок: его центр и радиус не передаются в DaData.
Пространственный фильтр применяется только к мероприятиям, вместе с ACTIVE Cooperation,
до пагинации и total_count. Фронт хранит выбранную область; геолокация необязательна.
При недоступности DaData — Unavailable, при лимите — ResourceExhausted,
без пустого успешного ответа. Ручной маркер и поиск мероприятий по уже выбранному кругу
не требуют повторного обращения к DaData. Поиск новых городов требует доступности провайдера.

Первичные источники географического подхода:
- [DaData](https://dadata.ru/api/suggest/address/) — поля, координаты и count.
- [ГАР ФНС](https://www.nalog.gov.ru/opendata/7707329152-fias/) — справочник; не готовый набор всех полигонов.
- [ST_Covers](https://postgis.net/docs/ST_Covers.html), [ST_DWithin](https://postgis.net/docs/ST_DWithin.html).

### 10.1. Загрузка аватаров и изображений поощрений

На карточку Volunteer, Coordinator, Event и Reward приходится не более одного изображения;
оно необязательно. Аватары двух профилей независимы. Общий ImageService.UploadImage
требует авторизованную сессию с user_id; анонимная сессия не подходит.
Клиент отправляет bytes data, не внешний URL и не имя файла с диска пользователя.
Сервер принимает JPEG/PNG размером от 1 байта до 5 МиБ и до 4096 пикселей по каждой стороне,
проверяет декодирование изображения и сам выбирает расширение .jpg/.png.
Некорректный файл означает InvalidArgument. Лимит чтения Connect при подключении — 8 МиБ,
чтобы помещалась и JSON/base64-передача файла; больший RPC отклоняется транспортом.

Сервис генерирует UUIDv7 файла и сохраняет его в
`storage/{user_id}/{image_id}.jpg` или `.png`. Каталог storage задаётся при запуске;
это локальная папка приложения, а не обязательный абсолютный каталог /storage в ОС.
Имя и владелец файла задаются сервером. ImagePath проверяет оба UUIDv7 и расширение;
относительные переходы, абсолютные пути и произвольные файлы не допускаются.
ImageData и ImagePath — модели значений, отдельного агрегата файла нет.

Ответ загрузки содержит image_path без префикса storage и image_url вида /storage/...
на HTTP origin бэкенда. Затем фронт передаёт image_path в avatar_path своего
UpdateVolunteer/UpdateCoordinator или image_path в CreateEvent/UpdateEvent и CreateReward/UpdateReward.
Отсутствующее optional-поле сохраняет картинку; пустая строка убирает привязку.
Для новой карточки пустой путь означает отсутствие картинки.
При CreateCoordinator админ может указать путь картинки, загруженной целевым volunteer_id.

Сервисы профилей, мероприятий и поощрений проверяют:
путь корректен, его user_id совпадает с владельцем изменяемой карточки и файл существует.
Для Event и Reward владельцем является координатор из сессии, для Coordinator при создании — volunteer_id.
Чужой файл — PermissionDenied, отсутствующий — NotFound, неверный путь — InvalidArgument.
Один собственный файл можно привязать к нескольким своим карточкам.
В БД хранится относительный путь, avatar_url/image_url вычисляются при чтении.
CoordinatorVolunteer и AdminVolunteer также возвращают avatar_url.

Запись файла и привязка к карточке — два отдельных вызова; загрузка сама не меняет карточку.
При отмене формы уже загруженный файл остаётся. Замена/очистка картинки и DeleteReward
не удаляют файл: в демо нет фоновой очистки, галерей, редактирования картинок или CDN.
Файлы читаются публично по /storage/...; допускаются только учебные публичные изображения.
Каталог исключён из Git; при перезапуске его сохраняют, при контейнеризации монтируют volume.
Масштабирование на несколько экземпляров потребует общего файлового хранилища через порт Storage.

Реализованы UploadImage, модели данных/пути, локальная запись и проверка существования,
привязка картинок к Volunteer, Coordinator, Event и Reward, общая аутентификация и раздача storage.
На фронте добавлен helper uploadImage; подключение поля выбора к формам — следующий этап UI.

## 11. Транзакции и минимальная защита

Проверки выполняются на сервере, фронт только показывает допустимые действия.
Это демонстрационный MVP без нагрузки: версии и автоматические повторы не реализуются;
согласованность параллельных команд обеспечивается блокировками строк. Практические параллельные действия двух ролей проверены e2e;
В callback изменяемые агрегаты загружаются с FOR UPDATE в согласованном порядке.
Вложенные операции работают в той же транзакции. Чтения остаются параллельными.
Атомарность нескольких изменений обеспечивает PostgreSQL через `Client.InTx` внутри репозиториев.
Сервисы передают callback с бизнес-логикой; транзакционные детали остаются в `infra`.
Технические ограничения уникальности сохраняются. Бизнес-проверки выполняются
в domain/app, не через CHECK в SQL:

| Команда | Атомарная область |
| --- | --- |
| Принятие/отмена/восстановление заявки | Event + Participation + места + доступ чата |
| Правка/отмена Event | Event + текущие заявки/места/доступ |
| CompleteEvent | Event + текущие участия + Wallet/операции всех присутствовавших |
| CreateRewardOrder | Cooperation + Reward/резерв + Wallet + RewardOrder/операция |
| Выдача/отмена заказа | RewardOrder + Reward/резерв + Wallet/операция при возврате |
| DeleteReward | Reward + PENDING заказы + резервы + Wallet/возвраты |
| TerminateCooperation | Cooperation + текущие участия/места + чаты + PENDING заказы/возвраты |

Уникальны (iss, sub), Coordinator по ID существующего Volunteer, пары Cooperation
и Participation. Для Cooperation агрегат дополнительно проверяет coordinator_id != volunteer_id.
Операции уникальны по (тип, participation_id/order_id); агрегат кошелька проверяет
coin_balance >= 0, confirmed_minutes >= 0 и переполнение при расчёте.
Перед изменением команда проверяет баланс, доступность места/остатка и сотрудничество.
Транзакция откатывается целиком при любой ошибке.
Списания и бронирования согласуются блокировками конкретных строк уже в демо.
При дальнейшем росте нагрузки можно сузить блокировку координатора при прекращении
сотрудничества до отдельных связей, сохранив единый порядок захвата ресурсов.

Обычная команда проверяет текущее состояние. expected_version и аналогов в API нет.
Фронт не делает отложенных автоматических повторов изменяющих состояние команд:
после неоднозначного таймаута перечитывает состояние.
Идемпотентность финансовых команд и уникальное основание начисления остаются —
это прямо требуется сценарием защиты, а не решение редких сетевых случаев.

## 12. Стиль proto и ошибки

Пакеты v1, явные json_name, отдельные Request/Response, типизированные даты,
presence для частичных обновлений. Поля группируются по смыслу,
внутри группы — по алфавиту; первичный ID, payload и служебные данные разделены.
reserved не используется по прямому решению пользователя.
В текущем прототипе номера полей идут подряд с 1 в порядке объявления,
включая общую нумерацию вариантов oneof с остальными полями сообщения.
Перенумерация разрешена до промышленного запуска. Go перегенерируется вместе с proto;
обновление TypeScript и фронта выполняется отдельным шагом по решению пользователя.

Optional-поля запросов приложения передаются по образцу Flida через `RequestOption` и `With…`.
RPC проверяет presence protobuf-поля и добавляет опцию только при его наличии.
DTO хранит `Optional[T]` из `internal/pkg/utils/value`; `Get()` возвращает значение и признак присутствия.
Нулевое значение, пустая строка или пустой список остаются переданными значениями.
Это применяется к обновлениям, фильтрам, поиску, сроку приглашения и snapshot истории чата.
Пустой набор опций сохраняет существующие правила контракта, включая допустимые пустые обновления.
Связанные поля расписания и ФИО сначала объединяются с текущими значениями, затем проверяются моделью.

Автор/владелец команды берётся из проверенной сессии. ID в запросе — адресуемый объект,
а не способ выдать себе роль. Отсутствующее поле Update не меняется;
пустая строка очищает только явно разрешённые текстовые поля.
Неизвестные enum/UNSPECIFIED в фильтрах — InvalidArgument.
Общая пагинация: limit=0 означает 20, допустимы 1–100; offset >= 0,
за пределами списка пустая страница. Исключения ListCities/SuggestAddresses описаны в proto.
total_count использует те же права/фильтры и снимок, что страница.
Между отдельными страницами каталога живые изменения могут менять состав списка.

Свои error.proto и коды ошибок не вводятся. Код RPC-ошибок перенесён из Flida
во внутренний пакет `internal/pkg/rpc-error`. Используются стандартные Google errdetails:
BadRequest, ErrorInfo, PreconditionFailure, ResourceInfo. Преобразование ошибок
приложения — на RPC-уровне. Исходные версии перенесённого кода: cookies —
`v0.0.0-20260812080531-f1cb15774239`, rpc-error — `v0.0.0-20260812080407-d4a1447d88b2`.

| Ситуация | Connect code |
| --- | --- |
| Неверное поле / минуты / неполный итоговый список | InvalidArgument |
| Нет действующей авторизованной сессии | Unauthenticated |
| Чужой объект / отсутствие требуемого профиля координатора | PermissionDenied |
| Неизвестный объект / удалённая карточка | NotFound |
| Повтор пары / конфликт request_id | AlreadyExists |
| Неподходящее состояние, рано завершать, нет места/остатка/баланса | FailedPrecondition |
| Цена изменилась после открытия карточки | Aborted |
| Недоступен DaData | Unavailable |
| Лимит подсказок / переполнен буфер стрима | ResourceExhausted |

В деталях ошибок не раскрываются чужие контакты, баланс, тексты чата или секреты.
Клиент использует Connect code и стандартные details, а не разбирает русский текст.

## 13. Состояние реализации и дальнейшие работы

Реализованы все текущие RPC Session, Volunteer, Coordinator, Admin, Cooperation,
Event, Participation, Reward, RewardOrder, EventChat, Geo и Image.
Полный сценарий MVP проверен на отдельной PostgreSQL 17, включая отсутствие повторного начисления,
защиту баланса, возвраты, отзыв доступа к чату и смену cookie при авторизации.
Проверены goose Up, повторный Up, Down до нуля и повторный Up.
Подробности текущих проверок — в backend-implementation.md.

Следующие задачи: подключить API к формам фронта, проверить вход с настоящим приложением Flida,
подготовить проверенные границы выбранных населённых пунктов, настроить HTTPS,
пройти браузерный сценарий и подготовить 3–5 слайдов защиты.
Справочник загружается из внешнего CSV; не подменять его несколькими учебными строками,
если интерфейс обещает полную выгрузку городов России; текущий MVP предлагает поиск подсказок.

Фронт: cookie credentials, единый Flida-вход и переключение режима кабинета,
отсутствие localStorage токенов,
перечитывание состояния после изменений, итоговая проверка CompleteEvent.
Кнопки учитывают состояние, но сервер повторяет все проверки.
API key DaData не попадает в клиентскую конфигурацию.

Завершение в демо также только после ends_at. Обхода времени нет.
Для короткой защиты заранее подготовить прошедшее событие с принятыми участниками,
а полную цепочку подачи/приёма до начала записать заранее или показать поэтапно.
Не выдавать заранее подготовленное состояние за только что выполненный полный цикл.

Контрольный список сценариев (часть проверена программным прогоном, полный UI — отдельно):
- полный путь 180 минут → +30 → покупка 20 → баланс 10;
- создание Coordinator для существующего Volunteer с тем же ID и общим ФИО;
- единая сессия, проверка координаторских прав и переключение режима без нового входа;
- разделение своих заявок/покупок и координаторских выборок через обязательный scope;
- поиск волонтёра админом по ID/телефону/почте без автоматической выдачи прав;
- запрет сотрудничества с собой через обычную заявку и приглашение;
- повтор завершения/начисления, недостаток средств и чужая роль;
- отсутствие приёма при заполненном лимите и покупки при исчерпанном остатке;
- отказ с приватной причиной и запрет повторной заявки;
- отмена/восстановление с освобождением места;
- запрет правки при активных заявках и завершения до ends_at;
- сохранение кратности длительности 30 минутам при изменении одной или обеих дат;
- фильтры будущих и прошедших по времени событий, включая ещё не завершённые координатором;
- повторное получение своей ссылки приглашения после перезагрузки кабинета;
- прекращение сотрудничества: отмены, возвраты, сохранение начисленного/выданного;
- удаление Reward: возврат PENDING, сохранение неизменяемых ISSUED;
- невидимость старой истории при первом/повторном входе в чат;
- успешное завершение стрима после CompleteEvent и переход клиента в режим чтения;
- city/radius фильтры, отсутствие координат и недоступность DaData.

Бизнес-вопросы текущего MVP закрыты. Конфигурация ключей, адресов, TTL сессий,
источник полной подложки и подготовка геоданных — работы этапа реализации,
а не дополнительные пользовательские функции.
