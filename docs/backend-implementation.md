# Реализация backend

Реализованы все методы актуальных proto. PostgreSQL/pgx/Squirrel; слои api/app/domain/infra.
Сервисы не вызывают другие сервисы. Состояние меняется через команды агрегатов.
Транзакция начинается в callback репозитория; SQL читает и сохраняет состояние.
Миграции запускаются вручную через goose; одна таблица — один SQL-файл. Автоматического применения нет.

| Область | Реализация |
| --- | --- |
| Session | Cookie/PASETO, Authentication + authn middleware, загрузка агрегата в context, ротация ID, удаление при закрытии |
| Volunteer/Coordinator/Admin | Flida iss/sub, регистрация Volunteer+Wallet, профили, фото, настройки, служебный поиск и выдача прав |
| Cooperation | Заявки, cooldown, многоразовые приглашения, прекращение и каскады |
| Event/Participation | Создание, фото, выборки, правки, отмена, принятие/отказ, восстановление, итоговый список и начисления |
| Wallet | Общий баланс, подтверждённые минуты, неизменяемые операции и снимки итогов |
| Reward/RewardOrder | Карточки, остатки/резерв, покупка, выдача, отмена/возврат, удаление с сохранением истории |
| EventChat | AES-GCM в БД, граница видимости после вступления, отзыв доступа, стрим и режим чтения |
| Geo | PostgreSQL-справочник с первичным импортом CSV, optional-полигоны, радиус, клиент DaData |
| Image | JPEG/PNG, локальный storage, владелец и проверка существования, публичная раздача |
| Запуск | Конфигурация, клиентский/admin listener, HTTPS или прокси, Docker Compose, seed |

Проверено:

- `go build ./...` и golangci-lint с конфигурацией Flida и строками до 120 символов.
- На отдельной PostgreSQL 17: goose Up, повторный Up, Down до нуля и повторный Up.
- На настоящих репозиториях: регистрация, координатор, приглашение, три мероприятия,
  заявки, принятие, 180 минут → +30 → покупка 20 → баланс 10.
- Повторное начисление/покупка/возврат/выдача, нехватка баланса, отказ APPROVED,
  cooldown и запрет сотрудничества с собой, каскады прекращения сотрудничества.
- Первый/повторный вход в чат, скрытие старой переписки, отзыв доступа и шифротекст в PostgreSQL.
- Connect JSON через Authentication: cookie и ротация, доступ к профилю/мероприятию,
  отказ анонимному клиенту, заполненные BadRequest для InvalidArgument и ResourceInfo для NotFound.
- Сохранение и повторное чтение города, центра, полигона и версии справочника;
  импорт 1103 записей открытого CSV и работа без исходного файла после импорта.
- Полная HTTP-сборка с подписанным учебным OIDC токеном/JWKS, загрузкой и привязкой
  изображения, выдачей файла, изоляцией admin API и повторным seed.
- Настоящий Connect-стрим: сохранённая история, EOF завершённого события,
  Unauthenticated при удалении сессии во время ожидания новых сообщений.

Первый прогон выполнялся временными программами. Воспроизводимые интеграционные сценарии
теперь находятся в `backend/integration`: все 58 RPC, изолированные схемы PostgreSQL,
учебные OIDC/JWKS и ответы DaData. Unit-тесты по договорённости не добавлялись.
Программная проверка не заменяет полный браузерный сценарий.
В проверке основной цепочки использовались учебные claims Flida; живые аккаунты и
квота DaData требуют внешней конфигурации и отдельного прогона.

Осталось для защиты: заполнить конфигурацию, подключить формы фронта и переключение ролей,
настроить HTTPS, подготовить геоданные и прогнать UI с реальным Flida-входом.
Список городов зависит от загруженного справочника; полигоны не выдумываются.
Списки демо фильтруются в памяти до пагинации, стрим читает БД каждые 500 мс,
файлы хранятся локально. Параллельные команды согласуются блокировками конкретных строк
PostgreSQL; общей очереди всех транзакций записи нет.

Сборка приложения перенесена из bootstrap в `cmd/hahaton` и разделена на init-файлы
по образцу Flida. Конфигурация перенесена в `internal/config`: envPrefix,
`caarlos0/env`, публичные поля Config/вложенных секций, типизированный ключ PASETO
и ключ шифрования хранения. Сервер и seed напрямую вызывают env.ParseWithOptions;
промежуточный environment и NewConfig удалены, настройки читаются через cfg.Section.Field.
Миграции выполняются только вручную. Секреты приглашений зашифрованы в БД;
повтор отправки из закрытого периода чата возвращает FailedPrecondition.

Добавлен `CooperationChange`: история статусов и retry_after сохраняется в той же
транзакции, что и Cooperation, включая первый запрос и принятие приглашения.
Повтор принятия уже активной связи не создаёт новую запись. Новая таблица —
`00016_cooperation_changes.sql`; к рабочей БД миграция автоматически не применяется.

Проверка запуска охватывает оба настоящих HTTP-listener, healthz и завершение по отмене context.
Границы временных фильтров и возврат невыданных заказов при прекращении сотрудничества
также проверяются интеграционно. Во всех NewNotFoundError передаются ResourceInfo по образцу
Flida: тип ресурса, известный идентификатор и описание; секреты приглашений не раскрываются.

Во всех 18 app-запросах с optional-полями используется подход Flida: RPC собирает
RequestOption через With…, DTO хранит Optional[T], сервис получает значение и признак presence.
Указатели больше не служат признаком optional в Request. Это охватывает 48 полей,
включая фильтры списков, административный поиск, expires_at приглашения и snapshot_sequence чата.
Дополнительный интеграционный сценарий проверяет пропуск, очистку и явный ноль.

Проверены составные модели: Profile собирается из моделей имени, даты рождения, почты,
телефона и Identity; строки claims разбираются клиентом Flida. DateOfBirth и логика
EmailAddress перенесены из Flida локально, без зависимости от её доменных пакетов.
История заявок использует типизированные статусы/автора, операции кошелька — тип/источник,
чат — ActorKind, набор требований — Requirement. Репозитории immutable-записей удалены:
хранение журналов включено в репозитории Cooperation, Participation и Wallet.
Публичные RPC и схема PostgreSQL при этом не меняются.

Проверены агрегаты и команды: идентификаторы, статусы, профили, изображения,
расписание и требования используются как модели. Команды завершения участия и
начисления принимают EventResult целиком. Participation хранит Optional[EventResult],
а PostgreSQL-репозиторий собирает его из сохранённых полей перед восстановлением.
Сериализация RPC и схема БД сохраняют прежний формат.

CORS настроен через github.com/rs/cors и connectrpc.com/cors по образцу Flida:
любой origin с credentials, официальные заголовки Connect/gRPC-Web и Authorization.
Обёртка подключена до аутентификации обоих listener. Cookie использует SameSite=None
при сохранении Secure/HttpOnly для запросов между разными сайтами.

Проверены все 59 сервисов и их Request/Response. Семь запросов с фотографиями
используют ImagePath/Optional[ImagePath], разбор строк выполняется в RPC; право на файл
и существование проверяются в app. Нулевой ImagePath обозначает очистку.
ListCities использует Page с прежними лимитами 100/1000. UploadImage создаёт путь
из типизированных ID. Межсервисных импортов и вызовов нет; каждый сервис начинает
работу с r.Validate. Частичные ФИО/расписание собираются в модели после чтения агрегата.


Проверен API-слой: proto преобразуется в доменные модели до вызова app, а сериализация
статусов, требований и типов операций использует явное соответствие констант.
Итог участия разбирается в serde с проверкой oneof. BadRequest указывает реальные
имена полей proto и индекс результата; ResourceInfo включает известные ID.
В Authentication используются сгенерированные Connect-константы Procedure.
Названия колонок во всех PostgreSQL-репозиториях объявлены как локальные константы
с суффиксом Column и используются в Select, фильтрах, SetMap и SQL-выражениях.


Проверен infra-слой: репозитории восстанавливают модели через конструкторы, ошибки
создания моделей дополнены именем поля и сохраняют причину через %w. Дата рождения
восстанавливается из компонентов PostgreSQL date без промежуточного форматирования;
изображения и требования сохраняются через String/Int32 моделей.
Save возвращает доменный NotFound, если UPDATE не нашёл агрегат. Нарушение уникальности
в репозиториях с ErrAlreadyExists отображается в эту ошибку; прочие ошибки БД не подменяются.
Клиент DaData сохраняет причину ошибок чтения/разбора и отображает их в Unavailable.

Все репозитории используют общий PostgreSQL-клиент. Вложенные InTx используют транзакцию
из ctx; независимых вложенных commit нет. Callback сохраняет связанные агрегаты и журналы
атомарно. Изменяемый агрегат повторно загружается с FOR UPDATE перед callback;
публичный Load остаётся обычным SELECT. В Client.InTx нет общей блокировки.
Обычные операции Event/Reward/RewardOrder/чата сначала берут FOR SHARE координатора;
изменения Cooperation и принятие/отзыв приглашения — FOR UPDATE координатора.
Совместимые shared-блокировки допускают независимые изменения внутри одного координатора,
exclusive-блокировка согласует прекращение сотрудничества с записью, покупкой и начислением.
Заказы захватывают Reward перед RewardOrder; чат — Event перед EventChat.
Все кошельки в пакетных начислениях/возвратах берутся по возрастанию volunteer_id.
Общий mutex EventChats удалён. Общие функции порядка блокировок находятся в
internal/infra/repository/locking; SQL строится через Squirrel. Сервисы друг друга не вызывают.
Проверка request_id для CompleteEvent и CreateRewardOrder выполняется внутри той же
транзакции, что и начисление/списание: параллельный повтор возвращает исходный результат.

Сетевые вызовы Flida/DaData и работа с файлами выполняются до транзакций.
Проверки изображения в UpdateCoordinator/Volunteer/Event/Reward перенесены перед Modify;
в callback применяется уже проверенный путь. Создание профиля, мероприятия и поощрения
также проверяет изображение заранее; UploadImage работает отдельно от БД.
AES-GCM и PASETO выполняются локально и не обращаются к внешнему сервису.
При добавлении клиентов это правило необходимо сохранять: внутри транзакций — только
БД, доменные операции и локальные вычисления.


Репозитории дополнительно покрыты отдельными интеграционными suites по структуре Flida:
`tests/integration/repository/<агрегат>/postgresql`, testify/suite + require,
`pkg/testcontainers/postgresql`, PostgreSQL 17 и Goose. 12 suites / 114 сценариев
проходят на новых контейнерах; суммарное покрытие репозиториев — 80,4% statements.
Тестовые объекты создаются через модели и команды агрегатов; состояния сравниваются
через публичные геттеры, даты — как моменты времени, набор требований — как коллекция.


E2E-набор `backend/tests/e2e/rpc` запускает PostgreSQL через общий Testcontainers helper,
применяет Goose и поднимает настоящий `hahaton.Run` отдельным процессом тестового бинарника.
Клиентский TLS listener и административный HTTP listener используются сгенерированными
Connect-клиентами. Только провайдеры Flida/DaData заменены локальным TLS-сервером;
в дочернем процессе trust store содержит его сертификат, без отключения TLS-проверки.
DaData endpoint задаётся `DADATA_ENDPOINT`, по умолчанию — официальный URL.
Сценарии создают данные через RPC и проверяют состояние только через RPC. Исключение
для подготовки — перенос starts_at/ends_at учебного мероприятия в прошлое прямым UPDATE.
Проверка покрытия сверяет успешные HTTP-вызовы со всеми 58 методами protobuf descriptors;
при запуске одного сценария через `-run TestRPC/...` проверка полного покрытия отключается.
Команды запуска и параллельные проверки описаны в backend/README.md.


Общая блокировка заменена блокировками строк. Новое интеграционное испытание
`event/postgresql/concurrency_test.go` удерживает изменение одного мероприятия и проверяет,
что другое мероприятие того же координатора успевает измениться до освобождения первого.
E2E `TestConcurrentMultiVolunteerCompletion` проверяет одновременные начисления двум общим
волонтёрам от разных координаторов при обратном порядке участников. До сортировки кошельков
сценарий воспроизводил взаимную блокировку; после сортировки обе команды завершаются успешно.
